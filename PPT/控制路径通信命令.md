当前C++版Runtime与仿真器Daemon之间通过Unix Domain Socket传递控制消息。控制消息主要分为五类：

1. 连接检查；
2. Device和内存注册；
3. Launch提交；
4. 状态查询与同步等待；
5. 诊断与Daemon生命周期管理。

# 1. 控制通道基本格式

控制通道使用：

```
AF_UNIX + SOCK_STREAM
```

每条消息采用长度前缀加JSON：

```
┌────────────────────────┬──────────────────────┐
│ uint32 little-endian   │ JSON Payload         │
│ JSON字节长度           │ 控制消息内容         │
└────────────────────────┴──────────────────────┘
```

例如：

```
{"cmd": "hello"}
```

响应采用相同格式。一般情况下：

```
{"status": 0}
```

表示成功；

```
{"status": 1, "error": "错误原因"}
```

表示失败。

需要注意：大规模指令、权重和Tensor数据不通过控制Socket传输，而是通过共享内存传递。

```
控制通道：命令、状态、Launch ID、错误信息
数据通道：Code、Args、Input、Weight、Output
```

# 2. 控制消息总览

| 类别       | 控制消息         | 主要功能                                |
| ---------- | ---------------- | --------------------------------------- |
| 连接检查   | `hello`          | 检查Daemon是否可连接、协议是否可响应    |
| 资源注册   | `register`       | 注册Device，并将Runtime内存映射到仿真器 |
| 任务提交   | `enqueue_launch` | 异步提交一次NPU程序执行                 |
| 状态查询   | `query_launch`   | 查询某次Launch的当前状态                |
| 单任务等待 | `wait_launch`    | 等待指定Launch完成或失败                |
| Stream等待 | `wait_stream`    | 等待指定Device和Stream下已知Launch      |
| Device等待 | `wait_device`    | 等待指定Device上已知Launch              |
| 全局等待   | `wait_all`       | 等待当前Daemon内所有已知Launch          |
| 诊断快照   | `snapshot`       | 导出Device内存和最近Launch信息          |
| 服务关闭   | `shutdown`       | 请求Daemon停止运行                      |

# 3. `hello`：连接与存活检查

请求：

```
{
  "cmd": "hello"
}
```

成功响应：

```
{
  "status": 0
}
```

功能：

- 检查Socket连接是否正常；
- 检查Daemon是否存活；
- 检查Daemon能否解析协议消息；
- 可作为Runtime初始化阶段的健康检查。

它不会：

- 注册Device；
- 映射共享内存；
- 创建Core；
- 提交Launch。

------

# 4. `register`：注册Device和Resident Memory

Runtime在提交Launch前，必须先注册目标Device。

## POSIX共享内存方式

请求示例：

```
{
  "cmd": "register",
  "device": 0,
  "memory_transport": "shm",
  "shm_namespace": "/zeus_v3_12345_0"
}
```

`memory_transport`省略时默认为`shm`。

Daemon根据`shm_namespace`推导共享内存名称：

| 区域         | 共享内存名称 |
| ------------ | ------------ |
| GDG0         | `_gdg0`      |
| GDG1         | `_gdg1`      |
| Core 0 WDRAM | `_wdram_c0`  |
| Core 1 WDRAM | `_wdram_c1`  |

处理流程：

```
Runtime创建共享内存
        │
        ▼
Runtime写入Code、Args、Input、Weight
        │
        ▼
发送register
        │
        ▼
Daemon打开并mmap共享内存
        │
        ▼
绑定到目标Device的GDG和WDRAM
```

成功响应：

```
{
  "status": 0
}
```

## `memfd`方式

当前实现也支持通过Unix Socket附带文件描述符注册内存：

```
{
  "cmd": "register",
  "device": 0,
  "memory_transport": "memfd",
  "memory_regions": [
    "gdg0",
    "gdg1",
    "wdram0",
    "wdram1"
  ]
}
```

同时需要依次传递4个FD：

```
FD 0 → GDG0
FD 1 → GDG1
FD 2 → Core 0 WDRAM
FD 3 → Core 1 WDRAM
```

这适合Runtime已经持有内存FD、不希望依赖全局POSIX SHM名称的场景。

`register`的作用不是传输Tensor数据，而是告诉Daemon：

> Device 0的模拟内存由哪些共享内存对象提供。

# 5. `enqueue_launch`：异步提交执行任务

请求示例：

```
{
  "cmd": "enqueue_launch",
  "device": 0,
  "entry_addrs": [
    1163936137216,
    1163936137216
  ],
  "num_cores": 2,
  "stream_id": 0,
  "execution_mode": "functional",
  "float2fixed_rounding_mode": "rne",
  "conflict_report_dir": "reports",
  "conflict_report_details": false,
  "fail_on_conflict": false
}
```

主要字段：

| 字段                        | 作用                                              |
| --------------------------- | ------------------------------------------------- |
| `device`                    | 指定目标Device；省略时使用当前连接注册的Device    |
| `entry_addrs`               | 每个活动Core的入口PC                              |
| `num_cores`                 | 活动Core数量，当前支持1或2                        |
| `stream_id`                 | 给Launch添加Stream标签，用于后续`wait_stream`筛选 |
| `execution_mode`            | 选择执行模式                                      |
| `float2fixed_rounding_mode` | 设置CT float-to-fixed舍入方式                     |
| `conflict_report_dir`       | 设置本次Launch的冲突报告目录                      |
| `conflict_report_details`   | 是否保存每条冲突明细                              |
| `fail_on_conflict`          | 是否将依赖冲突升级为Launch失败                    |

执行模式包括：

- `functional`；
- `trace-only`；
- `analysis-only`；
- `full-debug`。

成功响应：

```
{
  "status": 0,
  "launch_id": 1,
  "state": "queued"
}
```

此时只表示任务已经进入队列，并不表示执行完成。

```
enqueue_launch
      │
      ▼
分配Launch ID
      │
      ▼
放入Device任务队列
      │
      ▼
立即返回queued
      │
      ▼
Device Worker异步执行
```

需要提前完成的工作：

- Code已经写入Resident Memory；
- Runtime Args已经写入；
- AR30等参数已经Patch；
- Input和Weight已经写入；
- Output空间已经分配。

`enqueue_launch`不再传递`code_addr`和`args_addr`，这些信息通过Resident Memory及入口地址表达。

------

# 6. `query_launch`：非阻塞查询Launch状态

请求：

```
{
  "cmd": "query_launch",
  "launch_id": 1
}
```

典型响应：

```
{
  "status": 0,
  "launch_id": 1,
  "state": "running",
  "device": 0,
  "stream_id": 0
}
```

如果执行失败：

```
{
  "status": 1,
  "launch_id": 1,
  "state": "failed",
  "device": 0,
  "stream_id": 0,
  "error": "具体错误原因"
}
```

支持的Launch状态：

| 状态        | 含义                         |
| ----------- | ---------------------------- |
| `queued`    | 已提交，正在Device队列中等待 |
| `running`   | Device Worker正在执行        |
| `completed` | 执行成功完成                 |
| `failed`    | 执行失败                     |

`query_launch`是非阻塞接口，适合轮询或状态展示。

------

# 7. `wait_launch`：等待指定任务结束

请求：

```
{
  "cmd": "wait_launch",
  "launch_id": 1
}
```

该请求会阻塞，直到Launch进入：

```
completed
或
failed
```

成功响应示例：

```
{
  "status": 0,
  "launch_id": 1,
  "state": "completed",
  "device": 0,
  "stream_id": 0
}
```

功能相当于：

```
Runtime提交异步任务
        │
        ▼
继续执行其他Host工作
        │
        ▼
需要结果时调用wait_launch
        │
        ▼
等待NPU模拟任务完成
```

------

# 8. `wait_stream`：等待指定Stream下的任务

请求：

```
{
  "cmd": "wait_stream",
  "device": 0,
  "stream_id": 2
}
```

功能：

- 找到目标Device和Stream下当前已经登记的Launch；
- 等待这些Launch全部进入终态；
- 返回每个Launch的状态。

响应结构：

```
{
  "status": 0,
  "launches": [
    {
      "status": 0,
      "launch_id": 1,
      "state": "completed",
      "device": 0,
      "stream_id": 2
    }
  ]
}
```

重要边界：

> 当前`stream_id`主要用于Launch分类和等待筛选，Daemon还没有实现完整的Stream Scheduler、Stream优先级或Stream间依赖。

因此`wait_stream`表示“等待带有该标签的已知任务”，不等价于完整硬件Stream语义。

------

# 9. `wait_device`：等待Device上的任务

请求：

```
{
  "cmd": "wait_device",
  "device": 0
}
```

功能：

- 选择该Device上当前已知的所有Launch；
- 等待它们完成或失败；
- 返回Launch状态列表。

适合模拟：

```
Device Synchronize
```

但它只等待调用时已经登记的任务，不表示持续等待未来提交的Launch。

------

# 10. `wait_all`：等待所有任务

请求：

```
{
  "cmd": "wait_all"
}
```

功能：

- 选择Daemon中当前已知的全部Launch；
- 等待所有Launch完成或失败；
- 汇总返回状态。

典型用途：

- Runtime退出前统一同步；
- 测试结束前等待全部Device；
- One-shot流程收尾；
- 多Device任务的统一等待。

------

# 11. `snapshot`：生成诊断快照

请求：

```
{
  "cmd": "snapshot",
  "device": 0,
  "dir": "out",
  "reason": "debug"
}
```

当前会输出：

```
out/
├── gdg0.bin
└── last_launch.json
```

其中：

- `gdg0.bin`：当前Device的GDG0内容；
- `last_launch.json`：最近一次Launch信息和Snapshot原因。

主要用途：

- Launch失败后的现场保留；
- 检查Runtime写入的数据；
- 比较执行前后内存；
- 离线定位数据问题；
- 自动化回归失败留档。

需要注意：

> 当前Snapshot不是完整进程检查点，也不能用于恢复执行；它主要是诊断导出功能。

------

# 12. `shutdown`：停止Daemon

请求：

```
{
  "cmd": "shutdown"
}
```

功能：

- 设置Daemon停止标志；
- 通知Device Worker退出；
- 结束服务循环；
- 释放映射和进程资源。

当前实现收到`shutdown`后直接进入停止流程，不应依赖它返回普通成功响应。

典型使用场景：

- One-shot启动的临时Daemon执行结束；
- 测试环境清理；
- Runtime主动关闭模拟服务。

生产式常驻Daemon通常由外部进程管理器控制生命周期。

# 13. 一次典型Runtime交互流程

```
Runtime                                      Simulator Daemon
   │                                                │
   │ ① hello                                       │
   ├───────────────────────────────────────────────►│
   │◄────────────────────────────── status=0        │
   │                                                │
   │ ② 创建共享内存并写入Code/Args/Input/Weight    │
   │                                                │
   │ ③ register(device, namespace)                  │
   ├───────────────────────────────────────────────►│
   │                                  mmap并绑定内存│
   │◄────────────────────────────── status=0        │
   │                                                │
   │ ④ enqueue_launch(entry_addrs)                  │
   ├───────────────────────────────────────────────►│
   │◄──────── launch_id=1, state=queued             │
   │                                                │
   │                         Device Worker异步执行   │
   │                                                │
   │ ⑤ query_launch                                 │
   ├───────────────────────────────────────────────►│
   │◄──────────────────────────── state=running     │
   │                                                │
   │ ⑥ wait_launch                                  │
   ├───────────────────────────────────────────────►│
   │                     阻塞直到完成或失败         │
   │◄────────────────────────── state=completed     │
   │                                                │
   │ ⑦ 从共享内存读取Output                         │
   │                                                │
   │ ⑧ 可选snapshot或shutdown                       │
```

# 14. 当前协议没有的能力

为了准确说明功能边界，当前控制协议没有独立提供：

- `unregister`；
- `cancel_launch`；
- `pause_launch`；
- `resume_launch`；
- Launch优先级；
- 完整Stream调度；
- Stream间Event依赖；
- 动态修改Topology；
- Launch级远端路由覆盖；
- 通过Socket传输大规模Tensor Payload；
- 从Snapshot恢复执行。

其中Topology属于Daemon启动配置，不通过单次Launch动态改变。

# PPT精简表

| 阶段     | 消息             | 功能                           |
| -------- | ---------------- | ------------------------------ |
| 连接     | `hello`          | 检查Daemon是否可用             |
| 注册     | `register`       | 注册Device，映射共享内存       |
| 提交     | `enqueue_launch` | 异步提交NPU任务，返回Launch ID |
| 查询     | `query_launch`   | 非阻塞查询任务状态             |
| 同步     | `wait_launch`    | 等待指定任务                   |
| 同步     | `wait_stream`    | 等待指定Device/Stream任务      |
| 同步     | `wait_device`    | 等待指定Device任务             |
| 同步     | `wait_all`       | 等待全部已知任务               |
| 诊断     | `snapshot`       | 导出内存和最近Launch信息       |
| 生命周期 | `shutdown`       | 请求Daemon停止                 |

一句话总结：

> Runtime通过`register`建立内存关系，通过`enqueue_launch`提交任务，通过`query/wait`管理异步执行，通过`snapshot`保留诊断现场；指令和Tensor数据留在共享内存中，不通过控制Socket搬运。

# 页面左下：能够验证什么

建议只保留四项，每项配一个小图标。

### 指令解释正确性

- Opcode和字段能否正确译码；
- 寄存器、地址、Shape、Stride和数据格式是否正确使用。

### 指令功能正确性

- 控制流、数据搬运、向量和矩阵计算；
- 数据转换、舍入、饱和和写回行为。

### 指令协作正确性

- 多Executor之间的Mail；
- 多Core同步；
- 指令依赖和执行顺序。

### 最终结果正确性

- 输出数据与Golden比较；
- 寄存器和内存状态检查；
- 通过Trace定位首次偏差。

# 必须保留的边界说明

建议在页面最底部用浅灰色小字写：

> 验证结论适用于当前已实现的指令语义、给定输入及本次动态执行路径；不等同于RTL信号级验证，也不能证明未执行路径全部正确。

这句话很重要，可以避免“功能验证通过”等同于“芯片一定正确”。

# 一页PPT可直接使用的精简文案

## 指令功能验证：在硬件运行前验证NPU程序行为

> 仿真器按照ZEUS-V3指令语义执行编译器生成的指令流，检查指令执行后的寄存器、存储、同步状态和输出数据是否符合预期。

```
编译器输出
指令流 + 参数 + 输入 + 权重
          │
          ▼
    取指与指令译码
          │
          ▼
CT / LD / LW / ST / DT / VP / PE / SI / SO
          │
          ▼
更新PC、寄存器、L2、DDR、Mailbox和输出
          │
          ▼
Golden Compare + Dump + Trace
          │
          ▼
确认结果 / 定位首次差异
```

可验证：

- 指令字段、地址和数据格式解释；
- 控制流、数据搬运和计算结果；
- Executor Mail和多Core同步；
- 最终输出及中间架构状态。

验证产物：

- Golden Compare；
- Memory Dump；
- Instruction/Executor Trace；
- 错误位置与上下文。

边界：

> 指令功能验证关注架构可见结果，不展开RTL内部流水线、握手和信号行为。验证通过不等同于RTL或芯片验证通过。

汇报时可用一句话收束：

> 指令功能验证回答的是“这条指令执行后，软件可见状态是否正确”，而不是“硬件内部每个周期的信号如何变化”。

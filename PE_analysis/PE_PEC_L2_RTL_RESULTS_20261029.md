# PEC + L2 接入后的本地逐周期仿真：保留理想权重供给

2026-10-29。独立本地 testbench；不修改设计 RTL、不生成 wave、不提交远端任务。

## 1. 结果

三条连续 M1/N512/K4096、w1/c32/k4 合成计算，在真实 PEC、L2、AL1/MAC/OL1 和 group 输出控制连接下数值通过。**两次相邻 PEC 指令完成间隔都是 515 cycles。**

|命令|group0 类首 MAC|末 MAC|PEC 完成通知|相邻完成间隔|
|---|---:|---:|---:|---:|
|0|269|779|838|—|
|1|784|1294|1353|515|
|2|1299|1809|1868|515|

group1 类的首/末 MAC 分别为 266/776、781/1291、1296/1806，均早3拍，来自真实 PEC 路径深度差异。所有周期号按复位释放后的同一计数器记录。

每条命令的256次 MAC 接收，255个相邻间隔全部为2拍：
- 首末 MAC 的时间差：510拍。
- 包含首尾拍的采样窗口：511拍。
- 按256批、每批2拍计算的持续供给工作量：512拍。
- 相邻首 MAC、相邻 PEC 完成间隔：515拍。

511和512是端点口径差异，不是突破带宽下界。最后一拍MAC至下一条首MAC相距5拍，相比通常2拍多3拍；因此连续间隔为512+3=515。这个3拍是本模型的边界额外间隔，不能据此给所有生产指令统一添加3拍。

末MAC至PEC完成为59拍，但它与下一条计算重叠：例如第二条在784拍启动，第一条838拍才通知完成。因此不能将59拍再逐条累加成持续节拍。

## 3. 本轮接入了什么

流程如下：

```text
测试驱动初始化真实L2 SRAM
        ↓
测试驱动送合成PE指令
        ↓
pe_ctrl / pe_ctrl_logic / pec_pipelines
        ↓ 真实L2读请求和返回
group命令/激活FIFO及额度返回同步
        ↓
真实AL1 → 实际BF16 MAC → OL1
                           ↓
                     group sum → DT
                           ↓
              输出异步FIFO / 16笔额度控制
                           ↓
                    PEC结果汇合
                           ↓
                   真实L2写入/响应
                           ↓
                PEC完成通知；最终L2回读

理想权重源 ──每两拍一批，遇反压保持valid──→ MAC权重接口
```

实例化的生产模块包括：
- 完整 pe_ctrl wrapper，含 pe_ctrl_logic 和 pec_pipelines。
- z518_l2_l2buffer_ctrl 及其仲裁/缓冲/仿真SRAM依赖。
- 两个代表 compute group，每个有8个真实 pe518_top，实际执行AL1、16ALU/PE和OL1运算。
- pegroup518_inst_ctrl、pegroup518_sum、pegroup518_dt。
- 按 pegroup518_top 原连接接入的命令/激活 asyn_fifo_boreg、load_dma_518_pulse_cdc，以及输出FIFO/额度逻辑。

**两类代表group不是64个完全独立PE的全芯片模型。** PEC本身有完整8group接口：
- group0/3/4/7的PEC流水深度为5级，用代表group0计算。
- group1/2/5/6为2级，用代表group1计算。
- 在同数据、同权重源、同钟条件下，将各代表结果送到同类接口；逐拍检查类内命令、所有PE激活及输出额度信号一致。不能用此模型研究不对称MC返回或group间竞争。

权重源直接向每个PE送128个BF16值：每group8PE合计2KiB，全核等价16KiB/批；每两拍一批，对应条件容量8KiB/cycle。**本轮未接实际MC/GDG/Hub/WL1，不是从物理权重文件读取后测出的带宽。**

## 4. 等待统计：哪些等待影响计算

以下为代表group0的PE0、每条首MAC至末MAC窗口；pipe_ready监测ALU控制的第0路：

|统计|命令0|命令1|命令2|
|---|---:|---:|---:|
|权重valid但PE不ready|0|0|0|
|激活valid为0|0|0|0|
|ALU命令不ready|0|0|0|
|所监测ALU流水ready为0|0|0|0|
|MAC接收次数|256|256|256|
|MAC间隔大于2拍|0|0|0|

全程PEC→L2接口另有：
- 读请求valid但ready为0：**692拍**。
- 写请求valid但ready为0：**0拍**。

692拍是请求接口握手等待计数，**不能加到计算时间上，更不能直接叫作692拍MC/L2物理服务延迟**。它可能包含返回缓冲及消费者流控造成的接收限制；本轮未进一步按L2内部原因拆分。实际读请求与计算重叠，AL1预取/缓冲使各条MAC窗口内激活始终有效，所以这些读端等待未造成MAC供给空洞。

这也说明：判断瓶颈必须看等待是否传到关键计算路径，不能只看某个端口存在stall。

## 5. 对861问题的意义与边界

本轮提供了一个实际RTL反例：**在理想权重供给、没有其他L2客户端竞争的条件下，加入真实PEC激活装载和L2输出路径后，仍能达到515拍连续完成间隔。** 因此这些模块在所有条件下“天然必须占用约861拍”的说法不成立。

但不能将861−515=346拍直接归因于MC或WL1。尚未匹配的条件有：
1. 实际MC/GDG/Hub/WL1的服务、返回集合、数据整理和credit闭环。
2. 生产zbin发射和同步依赖；本轮共用一次形状配置，再连续送三条执行命令，未完整回放生产ISA程序。
3. 真实时钟频率/相位、多核竞争、其他L2客户端及远端RTL版本。
4. 权重路径内的指令接收：本轮用group完成反馈作为理想WL1指令消费边界，未模拟真实WL1命令生命周期。

因此下一项最有区分力的本地工作，是**保持本轮PEC/L2及数值验证不变，将理想权重源替换为真实返回链**，从每段valid/ready和MAC间隔看新增空洞最先出现在哪里。仍须明确MC服务模型是否真实；人为设置MC延迟只能用于敏感性对照，不能当作远端根因。

此前单group连续模型为517拍，本轮515拍；两者指令配置发送、接口边界不同，不能解释成接入PEC后优化了2拍。

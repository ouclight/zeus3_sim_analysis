## 2. 这改变了此前什么判断

此前只依据CRM偶/奇分频字段提出4:5比例，并假设AXI400MHz推导MC320MHz。新增文档明确给出了另一组绝对值：**Core/PE/AXI500MHz，MC400MHz**。两者比例相同，但PHY绝对延迟和时序寄存器按MC拍计数，不能把两种配置视作完全相同仿真。

远端任务trace的2500ps/core计数与文档500MHz也不同。文档说明设计目标，trace说明该观察时钟的时间单位；缺少远端时钟生成/force信息时，不能拿一个替代另一个。

本轮采用文档500/400MHz，与原同频400/400MHz形成单因素对照：MC频率保持400MHz，计算/core/AXI/L2侧由400提高到500MHz。

## 3. 台架、变更及验收

- 复用`pec_production_tiles_x8_20261103`已生成的RTL模型归档`Vtb__ALL.a`，包含真实单核8-group、64PE、PEC/L2、WL1索引与返回链、MC功能读控制、原厂DW模型。
- 只重新编译C++测试驱动，将core/MC半周期参数化；原RTL归档及来源文件不变。模型归档哈希见`model_identity.json`，修改见`driver_changes.patch`。
- 两组同一测试可执行文件，均INDEX=1、SEQUENTIAL=1，使用前三个生产tile索引/values地址及13个命令字。
- 相同M1/N512/K4096、BF16全1values/激活、原始归档索引页；每条MC仍有512笔values/块，Hub0另有1笔index/块。
- MC_PROFILE=1、tAA=7ns、open-page、刷新关闭等条件保持不变。PHY脉冲宽100ps，MC首次边沿相对本域半周期后加300ps；后续MC边沿间隔保持1250ps。
- baseline：CORE_HALF_PS=1250、MC_HALF_PS=1250，即400/400MHz。
- document：CORE_HALF_PS=1000、MC_HALF_PS=1250，即500/400MHz。PE、PEC、AXI、L2在本台架仍共享core时钟，不是额外验证了它们各自独立的时钟门控树。
- 数值、地址、ECC、256条MC请求/CAS/返回/credit守恒及排空、64个PE各768个MAC、1536个FP32输出逐位检查全部继承。测试驱动在assert失败时终止，不能通过总周期接近861代替正确性。

容量比较必须用同一时间单位：同频条件512个PE拍=1280ns；500/400MHz条件下同样512个MC拍=640个PE拍=1280ns。算术仍需256个有效PE拍，物理时间由640ns变为512ns。不能将640减512说成权重物理搬运变慢。

两组退出码均0。400/400MHz基线的完成、MAC窗口、请求、索引等待、256路统计及driver结果逐项与上一轮连续tile相等；检查见[comparison.json](artifacts/design_docs_replay_20261103/comparison.json)。

| 稳态完成间隔（PE拍） | 607 / 607 | **751 / 751** |
| 稳态物理时间 | 1517.5ns | **1502ns** |
| group0 MAC窗口（含端点） | 551拍 | 687拍 |
| 每块有效MAC拍 | 256 | 256 |

| 有效权重工作量/条件容量 | 84.35% | 85.22% |
| 有效算术/峰值 | 42.17% | 34.09% |

完整数值与地址门控：每组1536个输出FP32均逐位为4096；64个PE各768个有效MAC拍；Hub0的128条MC各1539笔，Hub1的128条各1536笔。接受、MC接受、CAS、PHY、ECC、credit及下游接收守恒，全部排空。

逐拍形态也符合时钟比变化：

```text
400/400：1 + 252×2 + 2×15 + 1×16 = 551拍窗口
         551 + 56 = 607拍稳态
500/400：1 + 126×2 + 126×3 + 2×19 + 1×18 = 687拍窗口
         687 + 64 = 751拍稳态
```

500/400配置下，通常两个PE拍与三个PE拍交替获得下一份MAC权重，对应平均2.5个PE拍，即5ns。基线通常2个PE拍，也是5ns。PE提频没有使MC更快供应新权重。窗口含端点的物理跨度为1377.5ns与1374ns，基本一致；首末MAC严格时间差应减去各自一个PE周期，不能混淆两种口径。

credit/MC统计进一步约束解释：

| 指标（3块合计） | 基线 | 文档配置 |
| --- | ---: | ---: |
| 256路MC `valid&&!ready`累计MC拍 | 39,168 | 39,168 |
| 256路credit halt累计AXI拍 | 39,168 | 146,176 |
| 256路返回接口被阻累计AXI拍 | 384 | 640 |
| 平均每笔credit生命周期（AXI拍） | 15.515 | 19.666 |
| 同上换算物理时间 | 38.788ns | 39.331ns |
| 最大outstanding | 15 | 15 |

这些累计量跨256路并包含启动/交接，不能直接当作某一块关键路径耗时，不能相加。MC受阻计数在相同MC频率下完全一致；credit生命周期的物理时间近似相同，而更快AXI侧更频繁碰到额度阈值。这支持当前模型受持续MC/返回供给约束，不证明credit窗口是远端861唯一根因。

### 4.1 对当前问题的实际结论

1. 新文档有价值：为500/400MHz及跨时钟FIFO提供明确设计依据，修正“只有4/5分频推测、没有绝对频率文档”的信息缺口。但部分文档明显早于当前RTL，不能把所有描述直接用于台架。
2. 按文档配置重跑后，计算侧提频25%，物理稳态仅减少15.5ns，耗时降低约1.02%。M1/k4并未因算术时钟提高而获得接近25%的吞吐收益；新权重供给的物理节拍基本不变。
3. 此处751与远端861使用不同PE周期，**不能说差距只剩110拍**。如果远端trace仍按2.5ns计，861对应2152.5ns；文档配置本地1502ns相当于400MHz下600.8拍，物理差距仍有650.5ns。该时钟配置没有复现远端生产耗时，也没有解决归因问题。
4. 本轮未启用完整芯片时钟门控树、APB100MHz配置过程、真实加密PHY、双核顶层或完整程序。为避免把多个因素混在一起，只改变了文档支持的计算/core/AXI/L2时钟。APB和rdrdy标注为100/400MHz不等于本轮补接了这些完整接口时钟生成。
5. 后续应将文档500/400与远端core trace400之间的差异作为配置核对项；不要继续把文档目标当作远端运行值，也不要扫时钟/返回延迟寻找一个接近861的数字。

本轮所有脚本、命令、日志及原始分析位于[实验目录](artifacts/design_docs_replay_20261103/)，无需重新编译triton_shared/triton_qmnpu。

## 6. M4 normal补跑：同一时钟对照

每个group的MAC间隔形态相同：1016个1拍间隔、7个20拍间隔，因而`1+1016+7×20=1157`；加20个块间空拍得到1177。7个长间隔内的非MAC拍合计133，对应窗口内activation-invalid计数，weight-valid保持有效。这里是接口级事件归类，未进一步将缺激活认定为AL1某个特定内部机制。

两组各6144个输出FP32均逐位为4096；64个PE各3072个有效MAC拍；8个group权重distributions=3072、pops=768，验证每份权重服务4次计算；256条MC均1536笔请求/CAS/返回/ECC/credit/下游接收守恒且排空。基线的完成、窗口、请求、复用、MC统计及driver字段逐项与历史1177结果相等，见[comparison.json](artifacts/m4_doc_clock_replay_20261103/comparison.json)。

本轮结论：**文档500/400MHz下M4仍为1177个PE拍；物理耗时减少20%，吞吐提高25%。** 与M1从607变751拍且物理耗时仅减少约1%形成受控时钟敏感性差异。M4重复使用权重，计算窗口内供数能覆盖需求；M1仍需高频新权重。该对比验证当前本地模型中两者限制方向不同，没有确认远端时钟，也没有定位861的剩余差异。

还应避免只根据credit halt认定瓶颈：两组M4的256路halt累计均513536个AXI拍、最大outstanding均15；同时计算窗口内缺权重为0、算术效率87%。这些累计状态包含上游预取满窗口和消费者复用/等待，不能独立证明供数限制了MAC。

### 7.1 必须优先对齐PHY行为分支

当前`code/rtl/gdg/gdg_unit/mc_ctrl_phy_wrap.v:287`的FPGA_MC_PHY分支，与部署宏匹配：

- `:302`固定`MODEL_RD_LATENCY=10`，对bank读数据和valid按MC时钟流水。
- `:339–357`及bank1对应逻辑推进读流水，非固定绝对7ns返回。
- `:416–442`在未定义FPGA_MC_DW时，用`mc_clk_5_tmp`驱动五态计数器，`clk_phase_cnt==1`生成返回选通，结合读valid生成rdrdy_n。
- 辅助时钟2GHz每5个上升沿循环一次，即2.5ns选通周期；**这个2GHz不是MC功能请求时钟，也不能称为MC带宽提高5倍**。
- 若MC为400MHz，10级流水对应约25ns量级的采样/传递过程，还需考虑CAS被采样的边沿、非阻塞更新及选通相位。不得直接写成每笔固定恰好25ns，更不能在旧7ns基础上再加25ns。

旧本地台架CAS后7ns产生100ps返回脉冲，与上述同步读流水和选通机制不同。这是新的、可据源码复现的模型差异；比继续任意调PHY延迟更具有确定性。

### 7.2 对时钟及加密PHY判断的修正

2GHz PLL force配合CRM分频和初始化，能够产生400/500MHz等最终时钟，但仍需核对实际选择及配置。不能看到clk_400M变量就认定所有计算模块都400MHz，也不能看到2GHz force就认定所有模块都2GHz。当前归档2500ps/core仍可作为观察时间尺度的证据。

**在该部署宏及相匹配RTL分支下，运行使用自带PHY行为模型，而不是加密hb_macro模型。**因此此前将“拿到VCS和加密PHY”视作对齐远端返回路径的必要前置条件过于宽泛；对这一分支，可以先本地接入实际10级读流水及2GHz选通行为。其它构建若关闭FPGA_MC_PHY则仍可能使用加密模型，不能泛化到全部环境。

该工程还给出simv默认构建位置`server/build_nowave/zeus518_sim/simv`及wave对应目录。它提供构建方式和源码，不代表本地已存在可执行simv，或历史任务必定使用该路径。

### 7.3 下一步及边界

先核对外部filelist实际引用的`mc_ctrl_phy_wrap.v`与当前副本的身份、宏是否被后续覆盖；再将当前MC功能读台架的7ns C++返回替换为对应同步读流水与选通，保留其它配置，比较每笔CAS、valid、rdrdy、FIFO可见和credit释放。应按MC边沿及2GHz辅助边沿驱动，不用一个经验25ns常量代替。

## 10. 部署PHY返回机制对照仿真（2026-11-04）

实验目录：[deploy_phy_replay_20261104](artifacts/deploy_phy_replay_20261104/)。本轮对齐已确认的返回机制，采用PE/AXI/MC均400MHz的原基线，辅助时钟2GHz。MC_PROFILE=1、原计算/GDG/MC编译归档、原数据及指令、单核8-group均不变；尚未替换EMU RAM或模拟完整CRM初始化。该时钟组合是受控实验条件，尚未确认为历史861任务的实际组合。

### 10.1 实现及独立校验

旧模型CAS后7ns产生100ps正脉冲。新驱动在下一MC上升沿采样CAS，推进10级valid/address流水，按部署2GHz辅助时钟和五态计数生成原始低有效rdrdy_n。行地址取低7bit，列地址取低7bit。接收DW FIFO使用rdrdy_n的**上升沿，即低有效脉冲结束边沿**；数据先经过组合ECC编码稳定，再提交时钟边沿。新驱动保留原MC边沿相位（首沿1550ps），辅助首沿250ps。

这是只读合成数据用例的C++行为复现，不是已经实例化完整mc_ctrl_phy_wrap：两bank使用相同合成内容，拒绝同时两bank读；不覆盖写存储、故障ECC和PHY全功能。驱动复位初始化为两态零，原RTL读流水无显式复位；本用例在指令前有充分空读冲刷。

`check_phy_rtl.py`直接从现有mc_ctrl_phy_wrap截取未修改的10级双bank读流水与五态选通RTL，以本轮lane0实际CAS时间/地址重放，逐笔对比FIFO采样边沿及地址。该检查独立于x8 C++模型，用于验证同步事件与极性；不能替代完整SoC版本核实。

第一轮因不必要的辅助边沿全模型求值而中断。随后一轮触发GDG数据断言，排查并修正了数据稳定/选通求值顺序及rdrdy_n极性；失败记录留在`failed_polarity_attempt`，不参与性能结果。生产RTL未修改。

部署源码中的实际路径为：

`boot.c:soc_load_firmware → 装载OSR/R52镜像 → soc_boot_and_serve → start_npu → 触发R52 BL2 → MCU完成NPU初始化并清0x40a0000c`。

具体证据：`server/vcs/sw/boot.c:583`先把0x40a0000c写1，再写启动控制，等待BL2启动并轮询MCU清零。该握手只说明初始化完成，不包含CRM寄存器快照。固件目录提供`r52_bootrom.ecc.romcode`、`bl1_el2.ssram.text`等镜像，未在本次检查中获得其CRM初始化源代码、符号映射或逐笔写寄存器记录。

`server/vcs/sw/hal.c:1673`虽有`npu_init_regs`表，但由`test_npu_core_clk_enable`测试路径调用；不能直接当成上述固件启动路径的实际写入记录。尤其不能将该NPU基址的寄存器表自动等同于NDDG CRM配置。

RTL可确认的是NDDG CRM相对偏移与复位值：`nddg_crm_reg_regs.v:333`之后，0x28选择值复位1（选择参考时钟），0x2c奇分频参数5、使能1、旁路0，0x30偶分频参数4、使能1、旁路0。`nddg_crm.v`连接奇分频至MC路径、偶分频至AXI路径；`crm_ckmux_2.v`明确sel=0选分频输出、sel=1选参考时钟。因此只有在固件已切换到PLL、保持上述分频并开启门控等条件下，2GHz PLL才对应MC400MHz、AXI500MHz。**复位分频值＋PLL force不等于运行频率已确认。**

另外，`server/rpc/src/grpc_service.cpp:544`允许每次launch传入范围为[0x10000,0x110000)的core配置写入；`zeus518_grpc_transport.cpp:1624`实际执行。它不是任意物理地址写接口，但说明审计运行状态仍应包含具体launch配置，不能仅查看启动文件。此证据本身不证明有NDDG CRM改写。

当前确认程度：部署源码中的PLL force、CRM RTL连接/复位值、固件启动握手已查实；历史861任务的固件身份、最终MC/AXI时钟、CRM初始化后实际值仍未确认。当前400/400/400MHz台架结果是已声明配置下的受控结果；MC320MHz也仍非已确认事实。后续若要封闭该差异，应取得匹配固件的初始化写序列或运行后的CRM读回/实际时钟周期记录，不能用871接近861反推这些值。

## 12. R52固件镜像解码及初始化写序列（2026-11-04）

### 12.1 格式与可信度

### 12.3 对时钟结论的推进与剩余边界

`zeus_crm_reg_regs.v:433`奇分频复位参数5、使能1、旁路0；本初始化段未改0x2c。`zeus_crm.v:576`的Core mux在sel=1时选择奇分频。结合当前部署TB强制Core PLL为2GHz，**当前本地部署镜像＋已查RTL在保持复位分频、无其他覆盖的条件下，可推导Core为400MHz**。这比此前仅凭辅助测试表更强，并与trace的2500ps计数单位一致。

不能把上述0x66000028的写入误认为NDDG的0x60800028写入：是不同寄存器块。本初始化段未写0x60800028/2c/30、0x68800028/2c/30，因而MC/AXI最终配置仍不能直接由此得到。另查`zeus_crm.v:1195`，DRAM时钟还经过mux：sel=0取外部`i_dram_clk`，sel=1取Core PLL奇分频；`zeus_crm_reg_regs.v:1343`的0x154复位0，本段也未写该位。不能仅因Core400MHz就认定WL1 MC亦400MHz。

## 13. 更早OSR/R52启动镜像追踪（2026-11-04）

### 13.1 镜像校验与架构

- R52 ROM共608个39位字；按RTL `ecc32gen.v`校验全部通过，得到2432字节ARM代码。此前仅截低32位的初步解析现已补上ECC校验。
- OSR ROM共16384个39位字，低32位呈RV32压缩指令程序。使用本机LLVM18反汇编，入口0x0跳0x80，启动段、调用、栈操作及读写辅助函数连续可解释。
- **OSR不能套用R52的ECC算法**：套用后16200字不匹配。当前未取得OSR内部ECC算法定义，不将此说成镜像损坏，也不宣称OSR校验已通过。低32位解码仍是待进一步硬件格式确认的静态证据。
- 当前`opt.txt`共256项，全部0。这只确认该加载文件内容，不证明所有启动硬件状态都为0。

### 13.2 找到了缺失的NDDG PLL切换代码

OSR启动代码在镜像偏移0x1da令a0=1，0x1dc直接调用0x44d8；随后0x1e0再次令a0=1，0x1e2调用0x4544。不是仅在镜像里搜到未调用函数。

两段函数结构相同：

1. 参数非零分支读取逻辑基址0x60800000或0x68800000，等待读值为1；与NDDG PLL就绪检查结构相符。
2. 读取基址+0x28，然后在a2中放0。
3. 尾调用0x4166写辅助函数，要求写`0x60800028=0`、`0x68800028=0`。
4. 参数为0的另一分支则写1，但上述启动调用传的是1，选择写0分支。

这里仍需准确区分逻辑配置地址与CPU实际总线窗口：0x4166辅助函数先写OSR窗口配置0x300003f0/0x300003f4，随后把逻辑地址低31位加0x80000000，通过0x3ef0辅助函数的`sw`完成写入。因此CPU侧访问可见0xe0800028/0xe8800028，不能直接将该CPU窗口地址误当成另一组CRM。完整NoC窗口译码尚未独立封闭；本轮确认的是程序意图及辅助函数地址转换。

审计脚本检查两处调用目标、实参1、两处写值0、共用写辅助函数和最终store指令，全部通过；提取的短反汇编见[osr_clock_evidence.dis](artifacts/firmware_crm_decode_20261104/osr_clock_evidence.dis)。这是静态指令检查，不是OSR整机运行记录。

### 13.3 对频率判断的影响

第12节“R52段未写NDDG时钟选择”仍成立，但现在有更早OSR阶段写0切换PLL的具体证据。结合已有NDDG RTL：0x28=0选择PLL分频，奇分频复位5、偶分频复位4，以及部署TB的2GHz PLL，**MC400MHz / AXI500MHz候选获得了更强的固件依据**，不再只是凭复位值猜测。

不过本轮不能直接宣布历史861任务的最终频率已证实：OSR ECC格式、完整窗口译码、其他启动代码是否覆盖分频和实际simv/固件身份仍需匹配。当前保存的871周期结果使用400/400/400MHz台架，不能把它重新标注为已经完全等同生产配置。也不能因找到PLL切换就直接把台架AXI改500MHz：应先确认台架各clock端口对应生产PE/Hub接收域还是NDDG AXI域，避免按同名误改。

本轮没有修改生产RTL、固件或已有仿真参数，没有用新延迟拟合861。

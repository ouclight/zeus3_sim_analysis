# Neg 算法实现、master 性能与候选方案综合报告

整理日期：**2026-11-06**。当前代码核对点：`feat/VP-support-neg-prg-kernel-only@06f1d4da72c96e006b40459e2ce53fdc49367cda`。

本文综合 2026-11-03～11-06 的实现说明、固定输入 CycleSim、代表性 trace VCS、Torch 参考与候选修复记录。**本次只核对源码、原始 JSON 和已有报告，没有新增仿真、构建或 VCS，也没有修改正式 kernel、wrapper、selector、编译器或 CI。**

## 1. 当前结论与阅读口径

1. 正式入口的 BF16、FP32、INT8、FP8 E4M3FN **全部仍采用 kernel-only PRG**，没有自动切到乘法、tiny PRG 或 CT XOR。它是独立 opt-in 接口，普通 `torch.neg` 和其他 kernel 内的 `-x` 不会自动受益。
2. 相对固定旧 master 算法，同 BLOCK、同实际 VP 的本地对照已经确认收益；代表性 RTL trace 也复现该方向。相对旧编译器优化版仍有 tiny 回退，不能称为所有 shape、所有参照均无回退。
3. FP32 `(-1)*x` / typed `-x` 在已测 Torch 数值与零符号标准下通过，部分中小长度更快；**NaN 原始位并不与本地 Torch neg 或 PRG 完全相同**。性能交叉点依赖 BLOCK/VP，尚未部署。
4. BF16/FP8 未修复 typed 路线有 `+0` 未变成 `-0` 的问题。kernel-only 修复已经找到，但当前修复版比 PRG 慢；修复成本由所有处理元素承担，不只是输入零时才发生。
5. INT8 直接整数表达式带 VP hint 的候选编译失败；浮点提升并显式回绕可正确运行。算术回绕已大幅降低旧 where 探针成本，仍未超过 PRG。
6. tiny PRG 缩块与 CT XOR 对极小输入存在收益，其中一批已有 VCS；CT 的额外 backing/物理字独占契约尚不适用于任意公共 Tensor。大输入 CT 明显落后。

本文中的 `N` 在性能表中均为**逻辑元素数 numel**；`B`/`BLOCK_BYTES` 为字节数。正式 raw-byte kernel 内部参数 N 则是总字节数，见第 3 节。所有加速比均大于 1 表示右侧候选更快，必须按表中注明的基线计算。

### 1.1 三类计时不能混用

| 证据 | 含义 | 可以说明什么 |
|---|---|---|
| 本地 CycleSim cycles | 固定模型中完整 leaf 的准备、DMA、计算、同步、循环与完成周期 | 同一实验身份内的受控性能与趋势 |
| VCS 指令 trace cycles | 首条指令到唯一显式 terminal TS，`end-start`、不加 1 | 同 RTL/simv/时钟/memory 身份的 RTL 诊断对照 |
| API/作业墙钟 | 还包含 JIT、分配、上传、排队或恢复等待等 | 本批未形成完整端到端性能结论 |

VCS 使用 400MHz、memory=mc；对应 observer 仍为 DRAFT、`metric_eligible=false`，所以是诊断实测，不自动成为 release 认证指标。不能用一张表的 CycleSim 分母除另一张表的 VCS 分子，也不能把作业墙钟当 kernel 时间。

## 2. 算子语义、Torch 兼容与支持范围

官方公开定义是逐元素取负，`y=-x`：[torch.neg 文档](https://docs.pytorch.org/docs/stable/generated/torch.neg.html)。以下三种标准需要分开记录：

| 层次 | 当前采用的解释 |
|---|---|
| 数值取负 | 普通数/subnormal 精确取负，Inf 正负互换；NaN 输出仍为 NaN |
| 固定 Torch 参考兼容 | 本地 `2.10.0+cpu`，NaN-aware 精确数值比较，并单独检查零的 signbit |
| PRG 的额外位级保证 | BF16/FP32/FP8 仅翻转符号位，其余位保持；INT8 按补码回绕取负 |

NaN payload/sign 不同，不应未经说明就算成 Torch 数值错误；但这些位可被 bitcast/signbit 观察，**也不能称完全不可观察或与特定 Torch backend 严格等价**。FP32 当前 PRG 在已测集合中与本地 Torch neg 逐 bit 一致；BF16 的部分 Torch CPU 路径会规范化 NaN，PRG 也不总与其逐 bit 相同。这里没有所有 backend 的统一 NaN 原始位承诺。

| dtype | 正式 PRG 的目标 | Torch 参考状态 |
|---|---|---|
| BF16 | `bits XOR 0x8000`，保留 payload，互换正负零 | 已测数值/零符号匹配；某些 NaN 原始位不同 |
| FP32 | `bits XOR 0x80000000` | 已测数值/零符号及原始位匹配；未穷举 2^32 编码 |
| INT8 | 除 -128 外输出 -x；-128 仍输出 -128 | 穷举 256 编码匹配 |
| FP8 E4M3FN | `byte XOR 0x80`，不 flush subnormal | 本地 CPU 无原生 neg/mul；仅用 FP32 提升后转回的推导参考 |

### 2.1 正式 wrapper 的接口契约

```python
from neg_wrapper import neg
y = neg(x, out=None, max_vp=4, profile=None, enable_jit=True)
```

- 支持四种 dtype 的 Zeus/privateuseone 连续 strided Tensor，任意 rank；按 numel 展平后返回原 shape、原 dtype。
- 空输入在参数校验后直接返回，不上传 tag、不 launch。非空输入/out 的逻辑起点须 4096-byte 对齐。
- out 必须预先匹配 shape/dtype/device，返回原对象；不 resize，不自动转换 dtype。
- 拒绝原地、部分重叠、非连续、autograd、未解析 neg/conj view。允许同 storage 中互不重叠的 byte 区间。
- singleton 维可有任意合法 stride。连续性校验后用 `as_strided((numel,), (1,)).view(torch.int8)` 规范化视图，不复制、不改变 storage offset 或原 metadata。
- 固定单 core，grid=(1,)；VP1/2/4 是单 core 内数据并行，不是双核。不宣称完整 `aten::neg` / `neg_` / autograd / dispatcher 集成。

历史 singleton stride 修复已测 27 项 host、192 个 host 组合和 24 次真实 wrapper Functional 启动；它解决的是启动前 dtype view 的错误拒绝，没有修改计算算法或 BLOCK/VP。细节见[接口修复记录](aten_neg_singleton_stride_fix_20261104.md)。

## 3. 当前 PRG 算法与真实计算流程

### 3.1 BF16/FP32：signed INT8 tag + 两条主要数据 VP

读取浮点的**原始 bytes**，每个 byte 按 signed INT8 的 r 解释，范围为 [-128,127]。不把原 Tensor 的 NaN 送入浮点运算链，而是在 FP32 中精确计算这些小整数。

```text
BF16 tag = [0, -128]
FP32 tag = [0, 0, 0, -128]
z = float32(r) + float32(tag)
PRG(z) = z + 256，若 z < -128.5；否则为 z
```

| byte 角色 | z 的范围 | PRG 结果 |
|---|---|---|
| 普通 byte，tag=0 | [-128,127] | 原样保留 r |
| 符号 byte，r<0，tag=-128 | [-256,-129] | r+128，清除 bit7 |
| 符号 byte，r>=0，tag=-128 | [-128,-1] | r-128，设置 bit7 |

最终都在 INT8 范围内，不依赖溢出转换。断点 -128.5 位于两个整数之间，避免实际输入等于分界点。

BF16 +1 的完整例子：

```text
0x3F80 -> 小端 bytes [0x80,0x3F] -> signed [-128,63]
加 [0,-128] -> z=[-128,-65] -> PRG 保持 -> bytes [0x80,0xBF]
最终 0xBF80，即 -1。
+0: [0,0] -> [0,-128] -> 0x8000，即 -0
-0: [0,-128] -> [0,-256] -> [0,0]，即 +0
```

两条主要数据 VP 是：A 将两个 INT8 输入转换/相加得到 z；B 执行 PRG 的分段 MUL/SUM1 并转回 INT8。A→B 对同一数据切片有依赖；不是两条独立并行操作。

“两条”不包含 LUT 装载、配置、MAIL、descriptor、DMA、循环等指令。多物理 VP 对不同切片并行执行同一数据链；完整 trace 的 VP 命令数远大于两条。

### 3.2 INT8：一条主要数据 PRG

```text
PRG(x) = -128，若 x < -127.5；否则为 -x。
```

仅 -128 进入第一段，直接生成可表示的 -128；不先生成 +128 再依赖硬件饱和/回绕。INT8 无 byte 位置角色，不需要 tag。

### 3.3 FP8：一条主要数据 PRG

原始 signed byte x 的分段为：

```text
PRG(x) = x+128，若 x < -0.5；否则为 x-128。
```

每个 byte 都是独立 FP8，所有位置均翻 bit7，无需 tag，也不对 FP8 数值先解码。

### 3.4 为什么 kernel-only 不需要旧编译器补丁

BF16/FP32 的 tag 实际存为 INT8，与原始 byte 输入同类型，能利用固定 master 已有的同类型 cast/add 融合。历史 FP32 tag 或混合输入 recipe 的额外 matcher 不再是这条表示的前提。

wrapper 按 device/module/BLOCK_BYTES 缓存 tag，LRU 最多 16 项；每个 tag 只覆盖一块。首次构造/上传、JIT、Tensor 分配、Python 开销不计入此前 kernel cycles，运行中的 tag DMA 则已计入。kernel 内还有一次 LUT/PRG 参数准备，不能说缓存 tag 已消除全部准备成本。

N_bytes = numel * element_size。每轮 `load -> 数据 VP -> store -> 指针前进 B`，循环 `ceil(N_bytes/B)` 次，尾块用 boundary_check。BF16 numel=65536、B16384 时为 8 块；VP4 每片 4096 bytes，即 2048 个 BF16。

BLOCK 是每轮任务量，不是 lane 数或单拍吞吐。已有 DMA/计算 overlap 不等于显式双缓冲，也没有“所有 DMA 已隐藏”的证明。

### 4.1 先澄清：没有自动选 VP2/VP4，不等于不能用

当前正式 profiles 中，四种 dtype 都有 `large1/large2/large4`，对应 **B16384、VP1/2/4**。例如小输入也能显式请求 `large4`；只要通过 wrapper 的预算、fold cap 与其他接口检查，就会按这个配置启动。它可能计算大量无效 padding，或者准备/同步成本更高，所以没有默认这样选。

当前 small profiles 只注册 VP1；没有提供 small2048/VP4 或 small4096/VP2 等公共 profile。leaf 的 VP_COUNT 允许 1/2/4，**但这不等于这些未注册的 BLOCK×VP 组合都已经完成编译合法性、正确性和性能验收**。若要使用，需要独立编译验证，不能直接当成现成正式配置。

`max_vp=4` 表示最多允许四个 VP，不是要求必须使用四个。显式选择示例：

```bash
# 即使 N=1024，也可以请求已注册的 B16384/VP4，供受控对照。
python python/zeus_examples/ATen/neg_select.py --dtype bf16 --numel 1024 --max-vp 4 --profile large4
# INT8 自动通常选 VP2，显式 large4 可测 VP4。
python python/zeus_examples/ATen/neg_select.py --dtype int8 --numel 65536 --max-vp 4 --profile large4
```

selector CLI 只输出选择结果，不执行仿真。实际调用可传 `neg(x, max_vp=4, profile="large4")`。

### 4.2 为什么要调 BLOCK，而不是统一越大越好

每个 BLOCK 容纳的逻辑元素数为 `T=B/element_size`，总循环数为 `ceil(numel/T)`。性能可用下面的成本关系理解，但它不是已拟合的预测公式：

```text
总成本 ≈ 一次性准备(B, VP)
       + 各块的 DMA / 数据计算 / descriptor / 同步成本
       - 实际已实现的 overlap
```

- **增大 B 的收益**：减少循环、descriptor 和重复同步；BF16/FP32 的 tag 只装一块再复用，更容易摊薄每块开销。
- **增大 B 的代价**：局部缓冲/中间结果占用更大，tag 数据更大；tiny 输入仍可能执行整块计算，尾块空位置更多。还受常量折叠、布局和编译合法性约束。
- **增加 VP 的收益**：不同 VP 处理不同切片，降低数据计算部分的持续时间。
- **增加 VP 的代价**：增加配置/参数分发/同步等成本；DMA 和共享带宽不会随 VP 数自动倍增。数据量不足时，计算节省可能覆盖不了额外准备成本。

例如 BF16 B2048 可容纳1024个元素，B4096可容纳2048个元素；N2048时从两块减成一块。B16384则容纳8192个BF16或4096个FP32。**容量解释为什么值得测试这些候选，但不能仅靠容量证明某个阈值最优。** B16384是已验证的大块配置，不是硬件理论最大值；B32768及以上没有在当前正式路径形成同等证据。

### 4.3 每档规则的依据与证据边界

| 当前规则 | 为什么采用 | 不能由此推出什么 |
|---|---|---|
| BF16 ≤1024：B2048/VP1 | 一块覆盖；沿用的小块基线，控制 tag/整块计算规模 | 不是 tiny 最优；第10节已有更小B候选获益 |
| BF16 1025..2048：B4096/VP1 | 用一块替代 B2048 的两块；N2048实测1469 vs 1623 cycles | 不是这个区间所有长度/VP组合都已逐点最优 |
| BF16 2049..8190：回到 B2048/VP1 | selector明确保留未充分测量交叉区间的小块基线，是保守兼容策略 | **不是证明B4096或多VP更慢**；块大小回切也不是理论规律 |
| BF16 ≥8191：B16384/预算内VP | 沿用已验证大块阈值；接近8192元素一块容量，代表点支持多VP吞吐收益 | 8191不是理论推导出的精确交叉点；8190/8191两侧仍应受控比较 |
| FP32 <4096：B4096/VP1；≥4096：B16384/预算内VP | 沿用保守策略；4096元素正好填满大块，实测大块VP4有效 | 不代表1025..4095范围已排除所有大块/多VP候选 |
| INT8 <4096：B1024/VP1；4096..16383：B4096/VP1 | 小长度控制准备成本，跨入中档时以较大块减少循环 | 4096是当前策略边界，不是多VP的硬件最低输入要求 |
| INT8 ≥16384：B16384，优先VP2 | N16384时VP2比VP1/VP4更快；当前采取保守VP2策略 | **并非VP4不能用**，N65536已有VP4略快的反例 |
| FP8 ≤1024/≤4096：B1024/B4096、VP1 | 一块覆盖相应容量，避免较小BLOCK多次循环 | 未证明每个小长度都是当前配置最优 |
| FP8 4097..32768：B16384，优先VP2；>32768且预算4时VP4 | 原专项扫描中，最多两个大块时VP2的准备/吞吐平衡更好，更多块时VP4开始占优 | 是冻结模型的实测交叉策略，不是所有RTL/版本的固定定律 |

BF16/FP32阈值在 kernel-only 移植时主要沿用此前策略，**不是本次 master A/B/C 表重新穷举拟合得出**。FP8专项另做了配置交叉扫描。不同策略的证据强度不同，不能统一写成“全shape自动最优”。

### 4.4 同一 PRG 内部配置对比：实际数字如何支持或限制策略

以下均为历史固定模型的本地 CycleSim，较小者更好。前六行来自 `neg_master_three_way_20261103/results/comparison.json` 的 kernel_only 字段，同一行只比较相同 dtype/N 的配置；不是 master 提速比。

| dtype / numel | 配置与cycles | 能说明什么 |
|---|---|---|
| BF16 / 2048 | B2048/VP1=1623；B4096/VP1=1469 | 此点增大块、减少循环有收益 |
| BF16 / 8192 | B16384/VP1=2667；VP2=2235；VP4=2129 | 此点多VP覆盖了额外成本，VP4更快 |
| BF16 / 65536 | B2048/VP1=23571；B4096/VP1=16070；B16384/VP1=11340；VP2=8171；VP4=7477 | 大数据同时受益于大块和多VP；不能把两类收益混称纯算法收益 |
| FP32 / 4096 | B16384/VP1=2667；VP2=2235；VP4=2129 | 大块一块容量下VP4在这个代表点有效 |
| INT8 / 16384 | B16384/VP1=1667；VP2=1594；VP4=1634 | 此点VP2优于VP4，多占VP并未更快 |
| INT8 / 65536 | B16384/VP1=4946；VP2=4546；VP4=4496 | 此点VP4较VP2快约1.11%，自动策略仍选VP2，属于保守取舍而非逐点最优 |

这些数字也说明：**不能仅凭“更多VP”判断更快，也不能仅凭某一长度的胜者给所有长度定规则。** INT8只有一条主要数据VP，BF16/FP32有两条且需要tag，其计算量与固定准备成本不同；FP8与INT8虽均为一字节元素，PRG参数与实测成本仍有差别，不能直接共享交叉阈值。

若后续要改selector，优先补BF16的2049..8190区间、现有阈值两侧和INT8 VP2/VP4交叉。固定输入/工具/实际VP，对每个长度比较全部已注册候选，再选代表点做VCS；本次仅补解释，**不改变算法、BLOCK、VP或阈值**。

## 5. 与固定 master 的差异和公平基线

### 5.1 A/B/C 分别是什么

| 标识 | 固定含义 |
|---|---|
| A：master 原算法 | `master@68fca1509f20b98ed0fe60de6e4fb4b6060cc105` 的 `ATen/neg/neg_*.py` 算法；用本轮固定 master 工具重编译 |
| B：旧编译器优化版 | 旧优化工具链的归档 PRG zbin，不用新编译器重编译冒充旧二进制 |
| C：kernel-only PRG | 与 A 相同工具链，signed INT8 tag / INT8、FP8 PRG；B/C 前批已验证结果明确复用 |

这里的 master 是**历史固定基线，不是 2026-11-06 远端最新 master**。当前分支后来 rebase，不会自动把历史 A/C 数据升级为最新 master 对照。

### 5.2 master 算法与当前算法

BF16/FP32 的旧 master 也处理原始 bytes，不是直接对浮点值计算 0-x：

```text
negative = min(max(-r,0),1)
flipped = r + 128*(2*negative-1)
output = r*(1-p) + flipped*p   # p marks the sign byte
```

它显式判断 byte 正负、构造翻转值并按位置混合。当前 tag 把 byte 角色编码到 z 的区间，再由两段 PRG 直接映射。INT8 旧算法有 MIN 特殊处理；FP8 旧算法还包含 subnormal flush/NaN 饱和逻辑。

### 5.3 两种比较不能混称

- **同 BLOCK、同 VP**：A/B/C 每轮 payload 相同，观察实现差异。旧 A 无 VP hint，仅给 --num-vp=4 仍可能实际只用一个 VP；多 VP A 因此只在测试副本加纯调度 hint，剥离 hint 后算法 AST 与原 Git blob 一致。
- **A 默认 BLOCK、同 VP**：A 保留 1024 元素的默认块，C 用 selector 配置，但 VP 仍匹配。这包含分块摊薄收益，不是仅 PRG 算术本身的收益。

实际 CSS 已审计 VP1=[4]、VP2=[4,5]、VP4=[4,5,6,7]；不能用 VP1 master 与 VP4 当前实现计算所谓同 VP 算法收益。

## 7. 其它算法总览：缺点与暂不考虑缺点时的成本

| 路线 | 思路 | 当前优点 | 缺点/限制与状态 |
|---|---|---|---|
| 正式 PRG | 字节角色 tag + 分段映射，或单 byte 直接 PRG | 稳定原始位语义，master 收益及代表 VCS 已验证 | tag/LUT 准备、tiny 启动成本；接口仍有限制 |
| typed `(-1)*x` / `-x` | typed load，FP32 算术，再转回原 dtype | 一条主要数据 VP，部分小长度快 | FP32 NaN bits 不同；BF16/FP8 正零符号不同；长输入可回退 |
| INT8 float+where | 特判 MIN 后转 INT8 | 256 编码正确 | scalar/选择等完整路径成本很高，不采用 |
| INT8 float+MAX 算术 | excess=max(-x-127,0)，显式减256回绕 | 相比 where 约降两数量级，256 编码正确 | 当前仍慢于单 PRG |
| BF16/FP8 零符号修复 | 最后一次浮点转换后按 raw bits 修 +0 | 成功版本通过当前数值/零标准 | 所有元素承担 mask/转换成本；BF16 还需昂贵重排 |
| tiny PRG | 算法不变，只缩 tag/暂存/BLOCK | 严格位目标，极小点已有 VCS 收益 | 跨块重复开销；不能固定 B64 覆盖所有 tiny |
| scalar CT XOR | 每 word 从外部读、CT XOR、写 | 极小点可省 PRG 启动 | 按 word 重复 DMA/同步，长输入很慢；backing/独占契约 |
| bulk CT XOR | 批量 DMA 后本地 CT XOR，再批量写 | 比逐 word 外部访问更有利于 tiny | 未生成 VP XOR；中等长度仍慢，奇数 BF16 有尾部 RMW |
| `0-x` / `-0-x` | SUB 浮点路径 | 表达简单 | 零符号及转换/NaN 行为不能直接满足位目标；缺少等价性能证据 |
| 向量 XOR 表达 | 张量 bitcast + XOR | 数学目标直接、位正确性清楚 | 已测表达实际降成本地 CT 循环，没有找到高吞吐 VP XOR |

“暂不考虑缺点”只允许比较计算成本，**不把输出不同或接口前提不同的候选算成通用替换成功**。没有实测的路线保留 N/A；一条表达式、一条数据 VP 或一次编译成功均不是收益证明。

### 8.3 INT8：裸整数与浮点提升不能混为一谈

直接 `-1*x`、`-x` 的整数带 hint 候选，VP1/VP4 共 4 配置编译失败：`vp_hint must annotate an operation lowered to zeus_high.vp`。这只是该带 hint 表达不可用，不证明所有无 hint 整数路线都不支持，也没有可报告的裸整数 cycles。

补充候选把 INT8 提升到 FP32，再处理 MIN 回绕。整数常量 -1 与浮点常量 -1.0 的 Torch dtype 行为不同，本报告没有用浮点输出冒充 INT8 正确结果。

## 9. 修复后再对比：可正确运行，不等于值得部署

### 9.1 修复的实际方法

- INT8：`n=-float(x); excess=max(n-127,0); y=int8(n-256*excess)`。只有输入 -128 时 excess=1，但所有元素执行这条算术；输出始终在 INT8 可表示范围内。
- FP8：转回 FP8 后 bitcast 到 INT8；以原始输入 byte 的 `max(1-abs(raw),0)` 识别 +0，在 raw 输出减128，再按 INT8 写出，避开最后的浮点零规范化。
- BF16：typed 输出后连续读入原始 bytes，局部拆成 low/high；`max(1-abs(low)-abs(high),0)` 仅对 +0 为1，构造高字节 mask、重排后连续写回。此路线通过功能但成本很高。

BF16 INT16 bitcast 路线留下未降完 linalg.generic 而编译失败；内层 stride=2 的高字节修复会改错邻近 byte（-0 写为 0x0080），明确拒绝；改成行 stride 又因 GDG pitch 不可表示被拒绝。没有悄悄带入编译器补丁规避失败。

### 9.2 普通非零输入也承担修复开销

以下 N=1024 的输入完全不含浮点零，仍有开销。INT8 修复为 MAX 算术；BF16 为最终成功 packed-byte 路线，FP8 为 raw-byte 修复。

| dtype / VP1 | PRG | MUL+修复 | NEG+修复 | PRG/MUL |
| --- | --- | --- | --- | --- |
| INT8 | 1009 | 1270 | 1269 | 0.7945× |
| BF16 | 1269 | 180766 | 180765 | 0.00702× |
| FP8E4M3 | 1009 | 1549 | 1548 | 0.6514× |

INT8 旧 where 版 N1024 为117484 cycles，算术版1270，约改善92.5倍；仍慢于 PRG1009。N65536/VP1 算术版37621/37620，PRG28414。

BF16 穷举65536编码：成功修复版11544517/11544516 cycles，PRG23571。FP8 N65536/VP4 修复版13759/13758，PRG4496。修复不是“只在输入0时变慢”，因为 mask、字节访问/重排、额外计算均按块执行；非零元素 mask=0 也不免除这些工作。

INT8 算术版穷举256编码匹配原生 Torch；BF16 packed-byte 版穷举65536编码匹配数值/零符号；FP8修复版256编码匹配推导参考。NaN bits 差异不因此消失。当前这些修复候选都没有超过同资源 PRG，不接正式 wrapper。

## 10. tiny PRG 与 CT XOR：极小输入的独立路线

### 10.1 缩 PRG BLOCK：算法不变，但跨块会退化

本地 B64/128/256/512/1024 扫描保留相同 signed tag/PRG。代表结果：

| dtype/N | 原 small / CycleSim | 已测较优 tiny / CycleSim | 原/tiny |
|---|---|---|---|
| BF16/1 | B2048 /1178 | B64 /1115 | 1.057× |
| BF16/32 | B2048 /1178 | B64 /1114 | 1.057× |
| BF16/33 | B2048 /1180 | B128 /1119 | 1.055× |
| FP32/1 | B4096 /1258 | B64 /1115 | 1.128× |
| FP32/32 | B4096 /1238 | B128 /1096 | 1.130× |
| FP32/256 | B4096 /1290 | B1024 /1176 | 1.097× |

BF16 N33 若固定B64则1392，比原1180更慢；FP32 N1024若固定B64则18565，原B4096仅1469。更小块并非通用更优，必须覆盖块边界、拟合元数据分派，而非只展示胜出点。

### 10.2 scalar CT 与 bulk CT 不是同一成本模型

scalar CT 对每word从外部读写；bulk CT 先批量DMA到本地，再逐word CT XOR、批量store。所测张量 XOR 也降为 CT循环，没有实际数据VP，不应标成“同实际VP1算法”。

| 路线 / 本地输入 | PRG对照 cycles | CT cycles | PRG/CT | 备注 |
|---|---|---|---|---|
| scalar CT FP32 N1 | 原small 1258 | 721 | 1.745× | padded独占backing |
| scalar CT FP32 N8 | 原small 1258 | 2338 | 0.538× | 每word访存/同步增长 |
| bulk CT FP32 N4 | 已测较优B64 1115 | B16 939 | 1.187× | 批量搬运路线 |
| bulk CT FP32 N5 | 已测较优B64 1115 | 最佳已测B32 1141 | 0.977× | 已发生交叉 |
| bulk CT BF16 N3 | B64 1115 | B16 1361 | 0.819× | 奇数尾部RMW |
| bulk CT BF16 N8 | B64 1115 | B16 947 | 1.177× | 完整pair |
| bulk CT FP32 N4096 | B16384/VP1 2667 | B256 220829 | 0.012× | 普通长度明显落后 |
| bulk CT BF16 N4096 | B16384/VP1 2189 | B256 110662 | 0.020× | 普通长度明显落后 |

这些 CT 比较是不同引擎路线的同单核/输入对照，不是同实际VP；CT实际数据VP=0。PRG“最佳”仅指该批已测配置，不是全配置最优。

CT harness 明确提供向16B取整再加16B的独立backing、输出物理word独占。BF16奇数尾部会读取逻辑范围外的同一个word，并保留邻居；即使sentinel不变，也不能证明任意Tensor子视图允许该读/RMW。未证明实际allocator/ownership契约前，不可接公共wrapper。

## 11. trace 给出的瓶颈线索与尚未获得收益的方向

BF16 N1 当前B2048/VP1的历史VCS总周期1001，重新归零后的关键窗口：

| 角色 | cycles |
|---|---|
| runtime参数DMA | 54..166 |
| tag DMA | 239..366 |
| LUT DMA | 246..382 |
| PRG engine参数装载 | 414..450 |
| 输入DMA | 471..582 |
| 首个有效数据加法 | 608..677 |
| 数据PRG | 703..839 |
| 输出store | 873..999 |
| terminal | 1001 |

414是参数装载，不是有效数据计算；首数据VP前608 cycles约占60.7%，但不是已证明可删除的浪费。tag/LUT DMA已经重叠，不能把127个tag周期直接当净节省。输入加载在准备/同步之后启动，可继续调查依赖，但不能未经证明删除MAIL。

同一tiny产物的PRG仍处理完整2048个byte位置，store只写有效2byte不代表计算也只处理2byte。大块VP4的首数据加法从993开始，但BF16总5701，准备被更多数据摊薄，不可套tiny比例。

以下未形成可部署新收益：

- 原生高吞吐 VP XOR：三个已测最小张量表达均落到批量DMA+本地CT逐word循环；不能据此否定所有潜在RTL模式，但没有可用VP XOR证据。
- 直接浮点SUB：需重新核验零符号/NaN和转换路径，暂无同契约收益数字；旧master原始byte算法不是简单SUB。
- PRG准备重排/提前输入DMA、DTM reshape替换CT repack、双缓冲：本综述引用的证据不足以宣称现已完成或再获2×；若继续，应独立探针、合法性/依赖证明、再测净收益。
- kernel内构造tag：历史BF16 N1=1402、FP32 N1=1597；相应外部缓存tag基线1178/1258，准备版没有被保留。历史FP32 tag转INT8仍有准备VP，tl.join常量还可能引入repack，不能仅凭tag值相同认定成本相同。

## 13. 当前决策与后续优先级

| 对象 | 当前建议 | 下一步需要什么 |
|---|---|---|
| BF16/INT8/FP8正式路径 | 保留PRG | 维护已测功能/边界与同VP收益，不为少一条指令破坏语义 |
| FP32 typed候选 | 可继续中小长度独立验收，暂不接默认分派 | 明确是否接受NaN位差异；与实际selector配置细扫交叉点，再选VCS代表点 |
| tiny PRG | 比继续大规模CT更有价值的独立增量候选 | 按dtype/容量/块边界设独立profile，确认相邻回退点及wrapper |
| CT XOR | 仅极小输入的受限候选 | 先证明真实backing/ownership；不向普通长度扩张 |
| BF16/FP8 zero修复、INT8 MAX | 保留可复现实验，不部署 | 只有找到明显更低成本的新表示才继续，不把正确等同于更快 |
| 最新master或发布收益 | 不沿用旧表冒充 | 固定新HEAD/工具，重新做同输入/同VP基线和批准计时协议验证 |

本报告是技术总结，不是合并/发布批准；没有新增吞吐估算、未经测试的阈值，也没有以不同VP或不同语义偷换基线。

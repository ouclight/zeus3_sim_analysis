# 真实 MC 读取控制＋GDG FIFO／返回／credit 闭环

日期：2026-11-02。承接 [MC请求接收空洞分析](PE_MC_REQUEST_HOLES_ANALYSIS_20261102.md)。不修改设计RTL，不重编Triton，不安装新工具，不提交远端任务。

## 1. 本轮完成了什么

本轮把此前分开的 MC 请求控制与 GDG 返回额度真正接成闭环：PHY模型不再按“GDG接收到请求”直接安排返回，而是等待**真实 MC RTL 发出实际读命令**，再按指定的返回延迟给数据。

已完成12组，每组连续4096笔请求，全部满足：

```text
来源接受数 = GDG接受数 = MC前端接受数 = MC读命令数
          = PHY模型返回数 = GDG返回数 = credit释放数 = 下游接收数
          = 4096
```

每笔返回的完整256位数据及物理命令地址顺序均检查，运行结束时队列排空、credit计数归零，没有GDG FIFO或PHY适配FIFO溢出。总计49,152笔请求。这里的数据是用于寻址、顺序和握手验证的地址标签，**没有运行BF16矩阵数值计算**。

## 2. 真实部分与模型部分

| 环节 | 实现 |
|---|---|
| 下游请求／返回控制 | 原始 `wl1_518_hub_mc_req_ctrl`，只有weight客户端启用 |
| GDG请求转换和输入CDC FIFO | 原始 `gdg_axi2frame`／`asyn_fifo_boreg` |
| GDG在途额度 | 原始 `gdg_flowctrl`，阈值15，无修改 |
| MC读前端、行／bank／页控制 | 原始 `mc_frame2frame_aux`＋`frame2array_aux` |
| VMC关闭时row展开 | 按原始VMC关闭公式复制row到两层 |
| 读命令到存储响应 | **显式PHY行为模型**：实际CAS命令采样后等LAT个MC拍返回 |
| MC内部返回FIFO | **显式DesignWare行为适配模型**：深度11，默认两级写指针可见延迟，另做三级对照 |
| GDG返回CDC FIFO及额度释放 | 原始 `gdg_rdata_buffer`／`asyn_fifo_boreg` |

这是一个MC通路的闭环，不是256条MC通路、双Core及完整PE程序。未实例化整个 `mc_subsys_top` 的ECC、BIST／初始化仲裁、刷新、VMC重映射；没有接AL1/MAC/OL1或16路Hub响应汇合。不能将本轮的512笔接收完成间隔称为生产PE完成间隔。

DesignWare适配模块不是原厂DW实现，也没有证明原厂时序相同。它提供真实存储、队列、同步延迟和深度检查，替代了前轮的empty占位；其指针同步是行为抽象，不是物理CDC可靠性仿真。当前生产依赖不齐的限制仍然存在。

## 3. 闭环数据流及额度释放位置

```text
来源valid/address
   ↓ 真实Hub MC请求控制
GDG rr_valid && rr_ready
   ├─ 真实输入FIFO入队
   └─ rdata_outstanding +1
           ↓ 输入CDC／排队
真实MC前端接收
           ↓ 行切换／预充电／激活等真实状态
实际gcas_rd命令及row/column/bank
           ↓ LAT个MC拍（诊断模型参数）
PHY返回strobe＋272位数据
           ↓ 深度11行为适配FIFO／同步
MC array_rvalid／rdata
           ↓ 真实GDG返回CDC FIFO
rdata_buffer_rvalid && rdata_buffer_rready
   └─ rdata_outstanding -1
           ↓ 真实Hub MC返回控制
下游接收
```

额度不是在“读命令发出”时释放，也不是等MAC／OL1运算完成才直接释放。它由真实GDG返回缓冲的接收握手释放；后级不接收可以通过返回控制间接推迟该握手。

计数达到15后，`flow_ctrl_halt`阻止新请求进入GDG。输入FIFO为16深，输入排队和等待MC接单都包含在这15笔生命周期内。

## 4. 来源、时钟与PHY参数

使用已核对的local/N512/k4 values地址子流：每512笔对应一个完整块的单MC份额16KiB，共八块；word地址128…4223。c32每块中部一个来源气泡。这里只发values，不混入索引、DIN或uscale请求。

默认splicing=1、打开页、pre_precharge=0、all-bank=0、bank_map=0xE4，时序输入使用前文列出的本地复位值tRCD6/tRP5等，非生产读回值。

Core固定400MHz。RATIO1显式设MC=400MHz，RATIO2显式设MC=800MHz；二者都是本地诊断设置，不代表已取得生产MC频率。PHY_LAT=0/4/14/23是预先选择的扫描值，未用861拟合。LAT0指采样CAS后同一MC返回处理拍发strobe，仍有半拍采样相位和0.1ns脉冲偏移，整个返回链不是零延迟。

CAS必须按每个有效拍采样，不能仅检测上升沿：连续读命令可能让CAS连续为高。本轮逐笔校验CAS输出的物理row／column／bank还原地址与来源一致，防止少计连续命令或人为复制请求数。

## 5. 实测对照

以下“完成间隔”是连续512笔返回块的**最后一笔下游接收时刻之差**，单位Core cycles；每组七个连续间隔均相同。它不是单块首末窗口，也不是PE指令耗时。halt等计数是整组4096笔运行总量，互相可能重叠，不可相加拆解总时间。

| 配置 | 完成间隔 | halt（Core拍） | MC不接单（MC拍） | GDG返回反压（Core拍） | 最大在途 | PHY适配FIFO最大占用 |
|---|---:|---:|---:|---:|---:|---:|
| r1_lat0 | 556 | 335 | 348 | 0 | 15 | 3 |
| r1_lat4 | 556 | 339 | 348 | 0 | 15 | 3 |
| r1_lat14 | 845 | 2652 | 348 | 0 | 15 | 3 |
| r1_lat23 | 1147 | 5068 | 348 | 0 | 15 | 3 |
| r2_lat0 | 513 | 0 | 315 | 0 | 11 | 3 |
| r2_lat4 | 513 | 0 | 315 | 0 | 13 | 3 |
| r2_lat14 | 529 | 126 | 315 | 0 | 15 | 3 |
| r2_lat23 | 633 | 958 | 315 | 0 | 15 | 3 |
| r2_row_all | 513 | 0 | 165 | 0 | 13 | 3 |
| r2_sync3 | 513 | 0 | 315 | 0 | 14 | 4 |
| r2_phase | 513 | 0 | 315 | 0 | 13 | 3 |
| r2_sink | 1024 | 4069 | 315 | 4088 | 15 | 3 |

### 5.1 固定真实控制器，长返回可以让credit成为持续限制

MC=800MHz时，LAT4→14→23：

- 完成间隔513→529→633 Core cycles。
- GDG halt次数0→126→958。
- 三组MC前端不接单均315个MC拍。
- GDG返回缓冲和Hub下游反压均为0。

因此，在**这个受控闭环中**，增加读命令后的返回延迟、叠加15笔窗口，确实会让持续吞吐下降；并非因为人为降低了MC命令服务II，也不是下游主动停止接收。

这里说的是已验证的机制，**不是生产861已定位为credit瓶颈**。实际PHY延迟、时钟比、ECC／额外流水和并行汇合均尚未匹配。

### 5.2 有halt不代表一定增加总耗时

MC=400MHz、LAT0和LAT4都达到15笔，也都有halt，但完成间隔均为556。部分额度等待与MC本身的换行等待重叠，所以不能把halt次数全部当作额外损失。

LAT14时完成间隔变为845，LAT23为1147，控制器不接单仍均为348个MC拍，而halt显著增加。845接近861只是条件模型的一个输出，**不是对861的复现或参数反推**。

### 5.3 后级反压也会通过额度释放反作用于供数

正对照 `r2_sink` 每16个Core拍人工停止下游8拍：

- 完成间隔1024 Core cycles；
- 下游反压4096拍、GDG返回缓冲反压4088拍、halt4069拍；
- MC自身不接单仍315个MC拍。

这验证另一条因果路径：下游接收变慢→返回缓冲不能及时出队→额度释放变慢→上游供数暂停。该50%接收模式是诊断刺激，没有证据说明生产WL1实际按此模式运行。

### 5.4 不把相位或行为FIFO参数当作已知生产事实

默认RATIO2/LAT4的间隔513；FIFO可见延迟两级改三级仍513，但credit最大在途数13→14；MC相位移动0.25ns仍513。行拼接＋all-bank对照也为513，但MC前端不接单从315降为165。

这些对照说明在该低延迟／较快MC条件下，局部变化可以被容量裕量吸收；不能据此排除生产场景中的CDC或地址敏感性。

## 7. 对861问题的实际推进

前轮只证明真实MC在某些配置下会接收停顿，本轮进一步验证了“这些停顿、命令后响应延迟、CDC和有限在途窗口”如何在真实GDG RTL中形成闭环。现在可以直接检查是MC拒收、窗口满、还是返回消费反压，而不是只从最终PE耗时猜测。

但这条链并没有在真实PHY配置下重现生产861。要把模型结论归因到生产，需要取得MC/GDG频率和运行寄存器，匹配ECC及生产返回FIFO时序，再核对实际PHY或远端只读计数。下一步应优先填这些身份／配置缺口；不应继续扫描LAT寻找一个恰好等于861的参数。

## 9. 规格约束下重新执行：400MHz＋tAA6/7/8ns＋真实ECC流水

### 9.1 本次具体修正

1. MC固定400MHz，Core固定400MHz，取消800MHz基线；仍明确Core/GDG频率是诊断设定，并非从生产TB读回。
2. PHY返回以实际CAS发出为起点，改成6、7、8ns绝对事件延迟；不再取整成14/23个MC拍。使用CAS输出寄存器更新后的1ps观察增量，再等待tAA；编码信号稳定另留1ps。每笔检查CAS→strobe相差tAA±2ps，不包含额外半拍采样偏移。
3. 加入原始09_12 `ecc_encode.v` / `ecc_decode.v`，配套使用交付目录内05_30/common/rtl的原始 `DW_ecc.v` 功能模型。返回数据带合法校验位，逐笔检查解码没有错误。这个模型来源版本记录在源码SHA清单，不假定与远端相同。
4. 实测ECC关闭也有一拍返回流水，开启是两拍，由RTL决定，没有人为追加16拍。只接ECC数据通路，不声称接了完整ECC地址记录／中断模块。
5. 默认返回FIFO行为适配的可见延迟仍为两级；三级敏感性对照沿用上一轮预设，未为匹配16拍调参。原厂DW FIFO未接入的问题仍保留。

### 9.3 典型16拍究竟对应什么

记录的延迟端点是MC前端 `hub_frame_vld && hub_frame_rdy` 到实际ECC返回有效在MC边沿被采样，和“GDG接单→额度释放”分开。

- 默认FIFO两级、tAA6/7ns、ECC开启：首笔15拍。
- 默认FIFO两级、tAA8ns、ECC开启：首笔16拍。
- tAA7ns、FIFO三级、ECC开启：首笔16拍。

因此模型冷启动返回处在规格典型16拍附近，且在预先给定的规格范围端点能达到16拍；这不是逐项证实原厂DW／完整mc_subsys_top等价，也不强制所有参数组合等于16。

更重要的是，首笔16拍不意味着连续读每笔都占16拍。第二个512笔块的MC前端→ECC返回分布：

| 配置 | 504笔同一行内部请求 | 4笔边界请求 | 另外4笔边界请求 |
|---|---:|---:|---:|
| tAA7ns／ECC开启 | 8拍 | 15拍 | 19拍 |
| tAA8ns／ECC开启 | 9拍 | 16拍 | 20拍 |

行内请求流水重叠；边界等待只影响少数请求。不能用规格“16拍”乘512，也不能只因16大于窗口15就断言credit必然主导。

### 9.4 逐项测出的额度生命周期

以默认tAA7ns／ECC开启的第二块为例，使用皮秒时间戳，统一除以2.5ns换算Core周期。以下区间按同一笔请求连接，均值可以相加；它们不同于互相重叠的全程stall计数。

| 区间 | 均值（Core周期） | 解释 |
|---|---:|---|
| GDG接收→MC前端接收 | 4.239 | 输入CDC及排队，不是纯CDC延迟 |
| MC前端接收→CAS命令 | 1.141 | 大多数直通推进，少数受真实行切换影响 |
| CAS→PHY strobe | 2.800 | 7ns规格响应，含约1ps模型稳定增量 |
| PHY strobe→MC核心返回采样 | 2.199 | 返回FIFO行为适配及MC边沿可见性 |
| MC核心返回→ECC返回采样 | 2.000 | 原始ECC开启流水 |
| ECC返回→GDG释放credit | 2.880 | 真实GDG返回CDC和接收握手 |
| 合计 | **15.260** | 与独立按GDG同域握手计数的均值一致 |

最大在途数15、部分周期halt，但完成间隔仍为556。前轮不带credit的同一默认读控制持续跨度也是556；不能把本轮约339个全程halt周期当作新增339周期或对应生产349周期差。tAA8ns只多出1周期，说明该范围的返回延迟和窗口并未导致数百周期额外退化。

### 9.5 对原有判断的更新

- 获得规格书后，长延迟扫描的845／1147等不再被当作生产延迟的依据；它们只证明机制可以发生。
- 规格约束下，本地默认路径已能接近接口条件下界，剩余与生产861的差异应从**未匹配的实际路径和配置**核查，而不能继续用“普通tAA很长”笼统解释。
- 单MC仿真尚未覆盖32路／多group响应汇合、完整Hub/DIN/uscale竞争、生产ECC完整包装／DW FIFO实现、真实GDG时钟及完整程序。这里列的是尚未匹配的边界，并非断言其中某项已是瓶颈。
- 后续最有辨识力的是把这个规格化lane接回已有多MC Hub/WL1返回汇合台架，先保持所有lane同配置，检查汇合是否新增持续损失；之后才加入有依据的差异。避免通过任意增大PHY延迟拟合861。

## 10. 多MC／双Hub汇合及生产边界流水对照

2026-11-02继续本地逐周期仿真。主入口为 [native.py](artifacts/mc_hub_spec_20261102/native.py)，正式结果为 [native_results.json](artifacts/mc_hub_spec_20261102/native_results.json)，摘要为 [analysis.json](artifacts/mc_hub_spec_20261102/analysis.json)。生产连接核查为 [production_path_audit.json](artifacts/mc_hub_spec_20261102/production_path_audit.json)。

### 10.1 范围及执行方式

将规格化MC/GDG/credit闭环复制为32条，接两个真实16路Hub collector、真实Hub返回link_pipe、WL1双Hub按序汇合及weight_data_format。对应**一个硬件group的两个Hub及8个PE权重输入端**；8个权重消费者始终ready，没有AL1/MAC/OL1计算，也不是8group／双核完整程序。

保留400MHz Core/MC、tRCD6/tRP5、打开页及实际CAS命令后6～8ns返回、真实ECC数据通路。PHY返回和原厂DW返回FIFO仍采用已披露的模型。每条MC通路的返回数据加入独立lane ID和word地址标签，既逐lane检查顺序，也在Hub／WL1合并点检查完整数据，防止“所有lane返回相同数据”掩盖错配。

连续执行三个N512/c32/k4的权重指令模型，每条MC共1536笔。来源在每块第256笔后空一拍；指令之间等格式器排空，再由测试驱动保持2个冷却计数后重启。这个指令驱动是测试代码，不是生产WL1/PEC完整调度；必须保留这一完成间隔边界。

完整台架在旧Icarus下初始化附近未能推进，终止该尝试，不作为性能结果。使用已有本地Verilator4.028，以C++事件队列驱动Core/MC时钟和PHY返回，全部设计RTL未修改；用post-eval CAS读命令安排响应，数据先经真实ECC编码稳定再发strobe，避免同事件数据／采样竞争。没有安装新工具，没有root操作。Verilator为两态模型；不能据此替代四态／原厂加密PHY验证。

### 10.2 验证完成

6组×32lane×1536笔＝**294,912笔MC请求**，各组均满足来源、GDG、MC、CAS、PHY、ECC返回、credit释放和下游接收守恒。各Hub分别合并1536包，WL1共接收1536包；每个PE权重输入端得到3×256份片段。合并前后数据检查通过，无FIFO溢出，结束时返回队列排空、额度归零。

### 10.4 直接观测到的汇合等待

Hub真实collector的有效条件为所有16路valid的AND；ready在齐备且下游接收时同时发给各lane。

```text
o_hub_weight_rd_dvld = &i_mc_weight_rd_dvld[15:0]
o_mc_weight_rd_drdy  = 全部齐备 && 下游ready
```

本轮计数定义：至少一路valid但未全齐为partial；全齐但下游不ready为blocked。partial与lane返回反压、credit等待可能重叠，不能重复相加。

- 全部相同tAA：两个Hub的partial、blocked均为0；WL1双Hub部分齐备计数也为0。
- 6～8ns交替：每Hub三块累计partial12拍、最长一次1拍，blocked0；部分较快lane观察到GDG返回缓冲／Hub MC返回反压12拍。实际观察到了“快路等慢路”的反馈，但数值受限，整体只达到所有lane8ns那一组的582，未出现持续放大到数百拍。
- 相位对照没有增加这些等待。不能外推为全部可能相位／地址条件都没有影响。

因此本轮否定的是“在这些规格一致、纯values、无背景流量条件下，16路汇合本身必然造成861”的说法；没有证明生产所有lane都具有同样的服务条件。

### 10.5 生产路径差异：实际补接了两段

源码核查发现初版台架缺少：

1. `wl1_518_hub.v:352`的权重AR入口`link_pipe`，depth1、set11。
2. `gdg_unit.v:385`的GDG读地址`forward_pipe`，宽度26，携带21位地址和5位len。

boundary_pipes受控组实际接入这两个原始模块；运行日志确认顶层和32条lane共33处FULL_PATHS开关均为1，防止配置未生效却误报结论。

相对uniform7，第二块片段窗口仍544拍，首块首片段59→61；连续块完成间隔580→582。因此这两段在当前台架带来每次重新建立供数的约2拍净变化，没有令持续供数大幅退化。不能把这一净差直接拆成每个模块各耗一拍的独立测量。

### 10.6 尚未等价的生产边界

源码静态检查：MC debug关闭时功能路径组合旁路；timeout正常功能模式对请求和返回组合旁路；功能流接MC仲裁器slot3，但BIST／初始化／rescan客户端是否在生产运行活动仍未知。没有把源码存在仲裁器当作已测竞争。

本轮还未匹配：完整mc_subsys_top与原厂DW FIFO／加密PHY、真实初始化及后台请求、完整V-cache索引流、全部硬件group和两个Core、生产WL1/PEC指令与AL1/MAC/OL1接收反压。当前没有证据把它们中的任一项宣布为861根因。

**推进后的结论：** 单MC改成32MC并接入真实双Hub／WL1汇合后，在规格约束下没有自然出现新的大幅吞吐损失。后续应优先将这条已验证的规格化供数链接回现有真实PEC/AL1/MAC/OL1台架，保持同一模型和计数，检查由真实计算接收与指令交接产生的反馈；并行核对生产版本／配置及真实额外请求。不能继续靠任意增加PHY延迟或人工周期阻塞解释861。


## 11. 将规格化供数链接入真实PEC、AL1、MAC、OL1：完成逐拍闭环

### 11.1 本轮实际接入内容

本轮按上一节建议完成连接，没有修改设计RTL或Triton编译器。权重接收ready由真实PE计算路径产生，不再固定为1，也没有用人为周期模式制造阻塞。

```text
生产WL1指令控制／地址生成
 → Hub AR流水 → 真实GDG地址FIFO／15笔credit
 → MC读控制器／行列时序 → CAS驱动的PHY行为返回 → ECC
 → GDG返回FIFO／credit释放 → 双Hub汇合／WL1格式器
 → 真实PE权重接收端
                                ↑ 真实AL1激活
                                ↓
                         MAC → OL1累加／输出
                                ↓
                         group输出 → PEC → L2
```

沿用已有PEC/L2计算台架的三条完整`M1/N512/K4096、w1/c32/k4`指令及BF16全1输入／权重，预期每个FP32输出为4096（`0x45800000`）。替换供数源，保留其指令、L2初始化、数据、数值校验及真实计算控制。

**规模边界：** 实例化两类代表性group，各8个真实PE，共16个PE，分别覆盖PEC激活／命令分发的两类流水深度；每group接两个Hub、每Hub接16条MC服务通路，共64条MC通路实例。这里的64不是64个PE，也不是完整生产MC共享拓扑。其余group的部分PEC输出由原台架的对称性映射处理，并带一致性断言；本轮不能称为完整8-group或双Core生产程序回放。

MC／Core均400MHz，MC相位在Core后0.3ns；使用前两节相同的真实MC读控制、ECC和GDG credit路径。PHY仍是实际CAS命令驱动、绝对`tAA=6～8ns`的行为返回；DW返回FIFO仍用已说明的行为适配器。没有接入原厂加密PHY、完整MC初始化／刷新／调试／后台客户端，也没有人为增加延迟拟合861。Hub AR和GDG AR边界流水全部启用，日志逐实例确认。

### 11.2 数值与请求守恒先通过

五组均通过以下门控，性能结论仅针对这些通过的运行：

- 每组完成三条指令；L2实际读回1536个FP32输出，全部逐位等于4096。
- 每个真实PE观察到768次MAC数据握手，即每条指令256次；16个PE均通过计数断言。
- 每条MC通路1536笔请求均经过接收、MC读命令、PHY返回、ECC解码、credit释放和下游接收，数量完全一致，无溢出；五组累计491520笔MC请求。
- 每group每条指令512次WL1请求，地址严格为`0x20000 + 1024*i, i=0..511`。该地址经现有映射后，每MC读取字地址128～639；三条指令重复这一权重块。
- L2完成192次激活读取、48次结果写入，并完成48个结果块、合计1536个FP32值的验证。全1数据检验数值／数量，不足以发现任意权重元素交换；前一节不同lane／地址标签校验作为供数链路补充证据保留。

### 11.4 实际ready／反压回答了什么

在第二、第三块首MAC至末MAC窗口内，两类group的代表PE均观察到：

| 逐拍观测 | tAA7ns | tAA8ns |
|---|---:|---:|
| MAC有效拍 | 256 | 256 |
| 权重valid但PE不ready | 0 | 0 |
| 激活无效 | 0 | 0 |
| ALU命令不ready | 0 | 0 |
| ALU内部`pipe_ready[0]`不ready | 0 | 0 |
| PE输出valid但group不接收 | 0 | 0 |
| 激活／命令／流水均就绪但权重无效 | 288 | 289 |

这里的288／289包含接口正常的每两拍供一次完整权重计算片段的节奏，**不是288／289拍可消除的额外等待**。每条指令256次全片段MAC，在理想每两拍供片段时，首末窗口含首尾为511拍；本轮544／545拍的额外窗口为33／34拍。

tAA7ns第二块在MAC索引63→64、127→128、191→192处，间隔由通常的2拍变成13拍，对应三处额外11拍，合计33拍。这些长间隔内激活、命令和计算流水仍就绪，权重valid未到。故本台架可将这33拍定位到**权重片段到达侧**，而非该窗口内的MAC／OL1拒收；不能仅凭此计数再把33拍全部指定成MC某一时序寄存器或credit独立等待。

请求端同时观察到第二块512次WL1请求首末窗口555拍，506次相邻请求间隔1拍，另有两次11拍、两次12拍、一次2拍间隔。请求空洞受预取、FIFO及credit反馈影响，与MAC长间隔不能直接逐项相加。

初始启动确实出现计算端反压：tAA7ns的group0在周期243～269连续27拍权重valid而激活尚未valid；`command_ready`及`pipe_ready`同时为1。后两块的MAC窗口未再出现这一现象。全程每个PE统计到权重拒收27拍，全部伴随激活未就绪，命令／流水拒收0，输出拒收0。tAA8ns对应26拍。Hub每路三块累计也有21～22拍齐备而下游未接收，说明本轮确实允许真实计算端反馈回供数链，不能将该计数视为常ready台架结果；这些层级的等待彼此重叠，不能求和。

lane tAA6～8ns交替时，每Hub仍只出现12拍部分齐备，均匀组为0；其块间隔与全lane8ns相同，没有自然放大为861。

### 11.5 对861的证据边界和下一步

**完成这次闭环后，当前规格化台架的真实AL1／MAC／OL1接收路径没有把持续周期拖到861；持续MAC窗口内也没有出现OL1相关流水不ready。** 因此，“只要接回真实计算端，k4也必然因OL1等待退化为861”在本轮条件下不成立。这个结论比此前固定ready更具体，但不是生产861根因已查明，也不是证明生产计算端永远不会反压。

本轮剩余与生产的差异应优先按证据核对，不能继续加人工延迟：

1. 核对远端simv的RTL／MC／PHY版本、真实时钟比和MC初始化配置，与本台架400MHz同频及当前寄存器值是否一致。
2. 将当前两类代表group扩展到实际8-group／双Core的真实共享MC路由，保留逐lane请求、汇合、credit及计算端计数；当前64条通路是两个group台架的实例数，不能当作生产无竞争证明。
3. 对齐生产完整values／index请求、权重地址跨块遍历及其他实际客户端，替换三次重复同一合成权重块的诊断程序；保留同样的窗口计数，找到哪一级首次偏离本轮544～545拍MAC窗口。

本轮没有改编译器、没有提交新远端任务，也没有把562当作当前生产kernel已经实现的性能。

**因此，在当前规格化MC／PHY和纯权重诊断程序条件下，接齐8-group没有引入额外持续等待，也没有复现生产861。** 这消除了代表group代接这一近似，仍不等于完整SoC／双核生产回放。实际生产时钟／寄存器、远端版本、完整values/index及其他客户端仍需有配置或请求证据支持，不能靠人为添加延迟或竞争拟合861。

本轮发现并单独复现了旧Verilator4.028对256位测试结束归约的代码生成问题；计算和数值完成后台架曾未退出。最终C++驱动逐字检查全部MC排空及原L2验证数量，全部门控保留，未修改生产RTL或生成计算逻辑。该墙钟超时不作为硬件阻塞证据。

# 单核8-group：规格化MC供数接真实AL1／MAC／OL1的逐周期验证

2026-11-02。上一轮为两类代表group；本轮保持MC／PHY、配置、指令、数据及数值门控不变，接齐8个真实计算group。

## 1. 结果

**五种条件下，8组与两类代表group台架的PEC完成间隔完全一致。接齐其余group没有引入额外的持续周期。**

| 条件 | 两代表group的PEC完成间隔 | 8个真实group的PEC完成间隔 | 差值 |
|---|---|---|---|
| uniform6 | [562, 562] | [562, 562] | [0, 0] |
| uniform7 | [562, 562] | [562, 562] | [0, 0] |
| uniform8 | [564, 564] | [564, 564] | [0, 0] |
| range6to8 | [564, 564] | [564, 564] | [0, 0] |
| phases | [562, 562] | [562, 562] | [0, 0] |

全部单位为Core周期，均连续执行三条完整诊断指令，取两次相邻完成间隔。
本轮仍未复现生产约861拍。
不能将本地结果作为当前生产kernel已实现的性能。

按每块4MiB和8192B/cycle条件容量，562拍对应`512/562=91.10%`有效权重吞吐，
564拍对应90.78%；按纯算术下界256拍，分别为45.55%和45.39%的有效算力。
这是工作量／时间／条件容量的比值，不是内部接口active计数。
M1每个权重仅服务一行输入，因此即使权重接口理想满供，持续算力也约受限于峰值的50%；
不能把本轮约45.5%的有效算力再解释成一半周期被OL1阻塞。

## 2. 本轮具体改了什么

```text
同一个真实PEC及L2
  ├─ group0：8个真实PE，自己的AL1／MAC／OL1、WL1、双Hub、32条MC通路
  ├─ group1：8个真实PE，自己的AL1／MAC／OL1、WL1、双Hub、32条MC通路
  ├─ ...
  └─ group7：8个真实PE，自己的AL1／MAC／OL1、WL1、双Hub、32条MC通路
        各组独立返回命令／激活额度与实际计算结果 → PEC → L2
```

合计64个真实PE、16个Hub权重请求／返回链、256条MC服务通路。
原先`0/3/4/7→代表0、1/2/5/6→代表1`的额度和输出代接全部移除。
逐条静态检查128条PE额度返回和24条WL1接受／结果返回连接，不再依赖组间对称性断言。

当前本地`pegroup518_x8_top`和`pegroup518_top`显示各group拥有自己的存储输出与WL1；
本轮按此扩展纯权重功能通路，没有人为引入8group公共MC仲裁器。
每group的Hub内MC请求控制、GDG credit、MC读控制／ECC仍采用上一轮连接。
未加入DIN／uscale后台负载，也未实例化完整SoC顶层，不能据此排除未覆盖的竞争。

`lane.sv`、`weight_return.sv`、`compute_group.sv`与两代表group台架逐字节相同。
上轮所用84个设计源码的SHA256核验全部一致。未修改生产RTL、kernel或Triton编译器。

## 3. 不变的模型与工作量

- M1/N512/K4096，三条完整`w1/c32/k4`指令；BF16激活与权重均为1，三条指令重复同一权重块。
- 每条指令每MC读取512个32B字，每group512KiB，8组合计4MiB。
- 每个PE每条指令256次MAC数据握手，每次对应128个标量乘加；全核每条指令2,097,152个MAC。
- 256条MC通路各32B/cycle的条件容量合计8192B/cycle，对4MiB仍为512拍供数下界。
  扩展group时工作量与接口容量同比增加，不能再把512乘8。
- Core与MC均400MHz，MC基础相位在Core后0.3ns；PHY实际CAS驱动，绝对tAA为6／7／8ns。
- 实际MC读控制、ECC、GDG请求／返回FIFO与15笔credit参与闭环；真实PE计算自行产生ready。
  PHY仍是行为模型，原厂DW返回FIFO仍由已有行为适配器替代。
- 混合组按lane编号使用6／7／8ns；相位组额外偏移0／0.25／0.5／0.75ns，均沿用上一轮规则。

没有周期性PE阻塞、人工延迟拟合或块间排空冷却驱动。

## 4. 正确性和请求守恒

五组均通过：

- 64个PE各768次MAC握手；共49,152次PE握手／配置。
- 256条MC通路各1536笔请求，接收、MC命令、PHY返回、ECC解码、credit释放、下游接收数量完全一致；
  每配置393,216笔，五组累计1,966,080笔，无FIFO溢出或额度上下溢。
- 每group逐条核对每条指令512次WL1地址：`0x20000+1024*i, i=0..511`，对应每MC字地址128～639。
- 真实L2读回1536个FP32输出，全部逐位为4096（`0x45800000`），而非仅检查输出valid。
- 192次L2激活读取、48次结果写入和48个验证读回块全部完成。

全1数据能检验计算数量与归约结果，但不能发现任意权重元素交换；不替代前序供数链不同lane／地址标签验证。

## 6. 每64次MAC处的较长间隔

每个MAC片段需每MC两个32B返回，因此64次MAC对应128个MC字。
当前映射列范围为128字，连续读取在128字边界切换；不能把它与Triton的page128概念直接等同。

前序单MC同配置日志显示，512个读命令在索引128、256、384处，命令间隔由通常1拍变为12拍，
每处多11拍、合计33拍。两代表group台架7ns的256次MAC则有252次间隔2拍、3次间隔13拍，
首末含首尾为544拍，比理想511拍多33拍；二者规律吻合。
这是已有真实MC读控制运行与计算端计数的交叉证据，不是人为注入等待。

本轮各group的实际较长间隔位置、长度、计算ready状态已在`compute_windows.long_gaps`中逐条保存，
可以直接与前序模型比较。长间隔处权重未到与MC命令空洞一致，不代表生产861全部来自同样的换行成本。
该证据也不能将Hub、credit和MC等待重复相加。

## 7. 目前能确定的范围

五种条件下，8组与两类代表group台架的PEC完成间隔完全一致。接齐其余group没有引入额外的持续周期。
本轮把此前“其余group由代表组代接”的近似消除，给出了真实64个PE接到PEC/L2的受控结果。
在本轮规格化供数条件下，没有发现接齐group后持续反压放大到861。

仍未匹配：远端simv版本、真实MC／Core时钟和寄存器、原厂PHY／DW实现、完整MC初始化／刷新／后台请求、

下一步应优先核对这些差异的实际配置或请求证据，再决定接哪部分；不能为得到861而添加未知延迟或虚构公共竞争。

## 9. 本轮排除的测试结束判断问题

首轮触发300秒墙钟超时，但实时日志已显示三块计算、1536个L2数值及256条MC请求守恒完成。
追查生成C++发现，旧Verilator4.028把台架256位`&lane_drained`生成成了零值比较，
使全部排空时结束输出反而为假。`reduce_probe/`独立最小探针确认全0输入返回1、全1输入返回0。

最终运行由C++驱动逐字要求8个32位`lane_drained`都为`0xffffffff`，同时要求实际L2验证计数48，
并继续执行全部MAC／请求／数据门控。没有使用错误的观察输出、修改生成计算逻辑或放宽完成条件。
相关生产归约信号检查见`termination_guard_audit.json`；本轮PEC额度、Hub汇合等相关归约宽度为4／8／16／32／64位，
未将这个256位测试完成探针当作生产硬件信号。
首轮超时和修正前日志只作为台架问题记录，不参与性能结论。表中均为修正后完整通过的运行。

### 10.1 当前可以确认的核内权重链

逐模块源码关系为：

```text
zeus_core_top_pwr
  → pe518_array
    → pegroup518_x8_top
      → 每group的pegroup518_top
        → 自己的wl1_518_top
          → 双Hub → wl1_518_top_mc_wrapper
            → 自己的gdg_unit → mc_ctrl_phy_wrap
              → mc_subsys_top + 本实例的PHY接口／模型
```

关键证据：

| 源码 | 位置与含义 |
|---|---|
| `zeus_core_top_pwr.v` | 8527：实例化本Core的`pe518_array` |
| `pe518_array.v` | 1719：实例化本Core的`pegroup518_x8_top` |
| `pegroup518_top.v` | 528：每group实例化自己的WL1 |
| `wl1_518_top.v` | 1020：实例化本group的MC wrapper |
| `wl1_518_top_mc_wrapper.v` | 505等：每条MC通路实例化自己的GDG；包括冗余通路映射 |
| `gdg_unit.v` | 560：非GDG FPGA替代分支中实例化本通路`mc_ctrl_phy_wrap` |
| `mc_ctrl_phy_wrap.v` | 184／198：实例化`mc_subsys_top`；450：非FPGA PHY分支实例化本通路PHY模型 |

这里不是两个Core在同一个MC读请求入口竞争的连接。核内已确认的共享点仍是各Hub每MC的DIN／weight／uscale轮询仲裁，以及MC内部功能／初始化／BIST等客户端。**存在仲裁器不代表该生产任务有其他客户端活动。**

双核可能通过上游NoC／WA访问使某个本地Hub出现额外DIN流量，但需要实际路由、地址及并发请求证据，不能仅因运行两核就构造这样的流量。此前DIN诊断确实能拖慢供数，仍不能当作生产861的根因。

### 10.2 双核包装层的意图与接口不一致

对`zeus_subsys_top_wrapper.v`中Core0、Core1实例进行去注释后的命名端口提取：

- 每Core各有256条旧式DRAM命名连接表达式。
- Core0使用`o_zeus02dram_* / i_dram2zeus0_* / io_zeus02dram_*`。
- Core1使用`o_zeus12dram_* / i_dram2zeus1_* / io_zeus12dram_*`。
- 两组DRAM网络表达式交集为0；这一包装层的连接意图没有把两个Core的DRAM信号直接合并。

但**不能将该意图升级为已展开生产双核拓扑**，因为当前文件之间不兼容：

1. 包装层2535～2542、3032～3039等位置使用`o_peg02dram_0_*`等旧命名；当前`zeus_core_top.v:307`等声明的是`o_peg0_wl12dram_0_*`，并对0／2等物理端口采用不同打包形式。审计发现每Core这256个旧DRAM命名端口均不在当前子模块头部声明中。
2. 包装层旧DRAM声明包含13路宽度，当前Core/PEgroup路径包含17／16路及冗余组织。没有找到在这一包装层内将两种形式转换的连接逻辑，不能混用宽度去推算带宽。
3. 当前Core声明`i_dram_clk`，包装层两个Core实例均未命名连接该输入；这证明接口副本不匹配，不证明远端运行中的MC实际没有时钟。

共享PLL参考输入`i_zeus_pll_ref_clk`并不等于两核共享一个权重请求队列，也不证明PE／MC同频。

### 10.3 顶层选择：不能把注释中的旧连接当作真实NoC路由

进一步去掉块注释后发现：

| 顶层文件 | 实际源码状态 |
|---|---|
| `Zeus518_top/top_pad_only/zeus518_top.v` | 655～9054行处于大块注释中；其中看似存在的`zeus_subsys_top_wrapper_u`和`zeus518_top_noc_wrapper_u`均不是有效实例 |
| `Zeus518_top/top/zeus518_top.v` | 有未注释的NoC wrapper实例，但未实例化上述双核／多核包装层 |
| 当前`noc/zeus518_top_noc_wrapper/rtl/zeus518_top_noc_wrapper.v` | 当前模块头没有名含zeus0／zeus1的端口，不能把旧top_pad注释模板接到它并宣称得到生产双核NoC |

导入的`filelist_zeus518_top.f → filelist_zeus518_top_module.f:66`选择的是`Zeus518_top/top/zeus518_top.v`；
`top_pad_only/filelist_top_pad_only.f`是另一个入口。当前`code/Zeus518/design`只导入了filelist，
清单引用的`$RTL_PATH/Zeus518/design/rtl/...`不能未经版本核对直接重定向成`code/rtl/...`并视为同一交付。

因此本轮没有得到一条可展开、与生产对应的“Core0／Core1 → 共享NoC／MC”的完整通路。
这不代表芯片没有NoC，也不代表远端无法运行，只说明当前可见文件不能证明它的实际编译连接。

| 对象 | 已核实信息 | 不能由此推出 |
|---|---|---|

| 本地MC／PHY | 真实读控制／ECC，CAS触发行为PHY，PE／MC均400MHz | 不能当作实际远端时钟／PHY配置 |
| 导入MC filelist | `MC_2025_09_12`；sim_model清单选择`PHY_IP_20251023` | 不证明远端simv采用该清单或用户重点查看的PHY09_12 |
| 861基线`b06c42294eae`归档 | VCS、`--num-cores 2`，6小时超时及trace | 提交命令没有RTL filelist／define／编译参数，不能反推出服务端simv的构建配置 |

还需区分以下宏的实际含义：

- `ZEUS518_FPGA_GDG_UNIT`：在`gdg_unit.v:138`选择AXI SRAM替代功能路径。
- `FPGA_MC_PHY`：在`mc_ctrl_phy_wrap.v:287`选择内置PHY返回替代分支；未定义时走原厂PHY实例。
- `FPGA_MC_DW`：进一步改变该替代分支的返回时钟生成。
- `TOP_NOC_DUMMY`、`EMU_SOC_NOC`：影响NoC wrapper相关分支。

普通`FPGA`宏不能代替上述专用宏；本轮台架也未实例化完整GDG wrapper，不能仅看`-DFPGA`就认定运行的是哪条完整SoC MC路径。

实际频率同样必须从配置确定：`zeus_crm.v:1200`的DRAM mux可以选外部`i_dram_clk`或PLL奇数分频输出；
PE／Core有独立选择。CRM内部偏移`0x154`控制DRAM源选择，复位值为0；`0x2c/0x30/0x34`分别涉及奇／偶分频及Core源选择。
源码中的选择结构不提供外部时钟实际频率，也不能用复位值代替生产初始化后的读回。

若MC每拍可返回的字节数保持不变，换算成PE周期时，供数下界按
`512 × f_PE / f_MC`变化。此前512拍条件明确包含PE／MC同频假设；没有实际频率读回时，不应靠扫比例去拟合861。

### 10.5 本轮结论和双核台架的接入条件

**当前没有发现已确认的跨核权重仲裁点，也没有证明双核竞争导致861。**
更具体地说，核内权重链是本地实例路径；旧双核包装层表达独立DRAM接口意图，但与当前Core接口不兼容，
且当前可见顶层入口没有把它与NoC连接成生产结构。

因此本轮没有直接复制两个独立8-group台架来宣称“已排除双核影响”，也没有构造额外公共MC去制造竞争。
要检验生产双核竞争，接下来需要对齐以下可审计材料：

1. 远端simv实际top/testbench名、有效递归filelist、defines及参数覆盖；最好带RTL/MC/PHY版本或源文件哈希。
2. 该testbench中两核各自的MC／PHY实例、存储初始化和可能共享的NoC／WA连接；应用kernel.zbin与两份权重文件不包含这些信息。
3. PE／MC时钟产生方式与实际频率、CRM及MC初始化写入／读回；不能用Zeus3应用回放init.json代替硬件配置记录。

拿到匹配连接后，单独Core0、单独Core1、双核并发三组保持每核工作量不变，对比每核请求grant、返回间隔、credit、MAC窗口和PEC完成时间。
若共享仅影响LD/ST而PE窗口不变，应归为加载／收尾开销；只有实际传入权重／激活／输出链的反压才用于解释PE稳态。
当前可继续进行核内有依据的受控仿真，但无法把未经匹配的双核复制实验作为生产跨核竞争结论。


## 11. 原厂MC／TRIM验证环境补充核查（2026-11-02）

**这些目录确实包含可用于继续校准本地模型的信息。**前一节缺少的是远端生产simv的实际连接和配置，不能据此把原厂IP验证环境也视为没有参考配置。本节为源码审计，未新增仿真，不改变前述562／564拍实测结果。

### 11.1 MC环境提供了什么

- `MC_2025_09_12/test/mc_env/env/mc_env.sv`组织frame请求、array侧监测、APB及scoreboard。它是MC单IP验证环境，没有完整双核PE／GDG共享拓扑。
- `env/mc_refm.sv`的main_phase内容被注释，是参考模型框架，不能直接拿它替代真实MC的周期行为。
- `tb/dut_inst.sv`实例化真实`mc_subsys_top`；`tb/model_inst.sv:25`实例化加密PHY，随后连接`LVS_FULL`阵列模型。MC输出的行／列／CAS延迟配置接入PHY，返回数据及ready由这条模型链产生。
- `flist/mc_env.flist`包含PHY、阵列模型、UVM及APB VIP。此入口比当前CAS触发的简化PHY更完整，但原始运行仍依赖其商业仿真器／库，不能把文件存在等同于当前本地已可运行。

### 11.3 原厂已有连续读效率测试

`tests/vseq/mc_performance_rd_vseq.sv`给出直接相关的测试方法：

1. 先执行公共初始化；随机选择是否切换close-page，并设置pre_precharge。
2. 打开performance_test_en，连续遍历行；每行从col=0读128笔，禁止随机列地址及wrap。
3. 分别记录请求valid&&ready和返回rvalid的时间；由bank选择持续时间检查效率。
4. 检查器写死trcd=6、trp=5，预期值为`128/(128+6+5)=92.0863%`，允许绝对误差0.01。
5. 每行首笔以外的请求，检查接收至返回的时间差不超过46。变量使用$realtime，当前tb时间单位ns，因此是46ns门限，不是46拍，也不是PHY tAA参数。

**检查器常量不等于DUT有效时序。**公共序列默认分支实际tRP=6，因此不能把上述92.09%不加条件地当作MC必达吞吐。检查器还用固定2.5ns换算拍数，适用频率也需要对齐。

这提供了独立于lm_head的原厂“128笔读流＋换页损失”校验依据，与本地已观察到的周期性行边界空洞相呼应；但它是测试意图与判据，不是远端861任务的实测，也不能把其损失率直接累加到PE时间。

### 11.4 TRIM测试能补充什么

`TRIM_CTRL_2025_09_12/test/trim_env/tests/vseq/trim_common_vseq.sv:86`提供power_up_init及寄存器写入／状态检查；hard／soft序列覆盖层数、spine reset、dump、TSV和校准控制。
用户查看的`trim_reset_test.sv:31`关闭scoreboard，并在序列运行中强制／释放rst_n、prst_n，验证复位恢复。它主要用于确认初始化和复位边界，不提供每笔权重读请求的服务时间。
因此TRIM适合用来核对“MC／PHY进入什么工作状态”，不能单独解释稳定运行中的861拍。

### 11.5 对后续工作的具体修正

下一项有依据的本地对照是：保留当前8-group、地址、数据、PHY返回模型及数值检查，只把MC时序换成原厂公共序列默认分支；分别比较每128笔边界、请求ready空洞、CAS间隔、credit和MAC窗口。页模式／pre_precharge应再单独对照，避免一次改变多个因素。
这一步不需要重编Triton或修改生产RTL，属于本地台架配置校准。若要复现完整原厂IP环境，还需按其filelist接入受支持的PHY／阵列模型与仿真库。
这些材料能减少模型假设，但不能替代远端simv实际filelist、双核连接和初始化记录。当前仍未证明861的精确成因。

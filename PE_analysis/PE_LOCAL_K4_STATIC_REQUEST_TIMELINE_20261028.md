# local/N512/k4：由分组、地址与RTL推导请求及消费时序

本节仅静态读RTL、枚举地址和循环，不运行RTL/functional仿真，不使用wave，也不以861拟合延迟。已有周期只在最后核对相对变化。当前本地RTL未证明与冻结simv逐文件相同，MC内部完整调度定义及运行时参数仍未闭合。

后续联合N/K/MTC复核见[M1的861-cycle稳态深入分析](PE_M1_861_CAUSAL_ANALYSIS_20261028.md)：`48+203×权重MiB+内部C边界数`同时描述已测匹配路径。该模型是经验补充，不改变本节513拍只是理想请求跨度的限定。

## 1. 真实分块：每轮16 KiB，不是整组1 MiB读完再换组

一条完整PE命令为`[1,4096]×[512,4096]ᵀ`，local V-cache/page128、KC、w1/c32/k4。

- 输出组g=0..3，各128个输出；这与硬件8个PE group是不同维度。
- 归约轮c=0..63，各64个K元素。
- 工作片段编号q=4c+g，计算`A[64c:64c+64] × W[128g:128g+128,64c:64c+64]ᵀ`，生成该128输出的一段部分和。
- 每片段128×64个BF16权重=16 KiB，256片段合计4 MiB。不会等G0完整K4096的1 MiB全部读完后才读G1。

实际顺序：`G0/C0,G1/C0,G2/C0,G3/C0,G0/C1,...,G3/C63`。源自WL1的MTK请求计数器先推进，再MTC；AL1坐标同样为W→K→C，w1时K先于C。

## 2. 每片段到底供给谁、地址是什么

8个硬件group以h=0..7编号；组内PE为p=0..7；PE内ALU为a=0..15；每ALU乘法lane为l=0..7。

```text
输出n = 128g + 16h + a
归约k = 64c + 8p + l
本次乘积 = A[k] × W[n,k]
```

h组处理其中16个输出；p PE分担8个归约位置。每PE收到16×8×2=256 B；一个硬件group合计2 KiB；8组共16 KiB。

在当前权重镜像中，tile0 values起点B=1 MiB，具体BF16元素的字节偏移：

```text
B + (4c+g)×16384 + h×2048 + (8p+l)×32 + a×2
```

已按此公式从实际文件抽查121个边界/内部元素，与normal布局还原的同一W[n,k]位模式全部相同。这里的镜像offset不等于所有控制器共用一个全局GDG读口；每硬件group使用自己的地址空间和Hub。

同一硬件group内，每个片段2 KiB由两次双Hub传输组成，每次Hub0/Hub1各512 B。每Hub又是16个MC各32 B。第一、第二份返回必须经整理后才组成8个PE各256 B的权重输入；这引入固定收集延迟，但在连续返回条件下仍可每两拍生成一批，不意味着每两拍后还要强制空一拍。

## 3. 可以直接算出的理想请求时间表

定义T0为**第一次values请求被WL1下游接受的时刻**，不含指令初装、初始索引读取和此前指令残留。假设双Hub模式、请求ready持续为真、索引已就绪、不发生index cache页切换。

每片段请求两次，b=0,1。由请求计数器和门控得到：

```text
t_request(c,g,b) - T0 = 2(4c+g) + b + floor((4c+g)/128)
```

最后一项来自c32 minitile内部边界：C31/G3第二次请求成功后，`tc_cnt_change_flag`会在下一拍屏蔽请求，再恢复。MTK3→0的普通组切换没有对应的固定屏蔽项；page128的32个索引项都在一次缓存的128项以内，也没有每个片段一次远端索引往返。

设L为请求被接受至对应双Hub数据齐备的固定延迟，F为其后的格式整理/FIFO等公共固定延迟，S=L+F+1。只在持续返回、激活/命令/下游ready的假设下：

| 片段 | 所需权重 | 镜像中相对values起址 | 两次请求拍次 | 理想MAC接受时刻 |
|---|---|---:|---:|---:|
| G0/C0 | W[0:128,0:64] | 0 KiB | 0、1 | T0+S |
| G1/C0 | W[128:256,0:64] | 16 KiB | 2、3 | T0+S+2 |
| G2/C0 | W[256:384,0:64] | 32 KiB | 4、5 | T0+S+4 |
| G3/C0 | W[384:512,0:64] | 48 KiB | 6、7 | T0+S+6 |
| G0/C1 | W[0:128,64:128] | 64 KiB | 8、9 | T0+S+8 |
| G3/C31 | W[384:512,1984:2048] | 2032 KiB | 254、255 | T0+S+254 |
| 内部切换 | 无请求 | — | 256空一拍 | — |
| G0/C32 | W[0:128,2048:2112] | 2048 KiB | 257、258 | T0+S+257 |
| G3/C63 | W[384:512,4032:4096] | 4080 KiB | 511、512 | T0+S+511 |

这是权重请求发生器的理论接受拍次，**不是已观测MC发命令拍次，也不是完整PE生命周期**。512个values请求加1个内部气泡，总请求跨度513拍；初装、公共L/F、MAC/OL1排空、minitile及指令交接还要考虑重叠关系，不能把这些数字直接逐项相加成稳态。

重要区别：G3比G0晚6拍是有序流水的正常位置，不是额外stall。正常G3应在轮到它时准备好；并不要求四组在G0开始前就都进WL1。请求计数器依据请求握手推进，不依据MAC完成推进，因此能在MAC算前面的片段时预取后续片段。

## 4. OL1反馈是否仍会挡住这张理想时间表

同一ALU交错维护g=0..3四个输出的局部部分和。按上表，相同g在相邻C轮之间相隔8拍；沿用已核查的局部约4拍反馈模型，8拍大于反馈间隔。因此在minitile内部、其它路径ready时，不需要因为这一局部反馈再插空拍。

仅为表达必要约束，可写：

```text
MAC_time[q] >= max(
    weight_ready[q], activation_ready[q], command_ready[q],
    MAC_time[q-1] + 1,
    MAC_time[q-4] + D_feedback
)
```

minitile切换、OL1输出及ping/pong等约束需另列，不包含在这个简化max式中。把固定L统一加到所有weight_ready，只改变整条流水相位，不自动使每轮G3迟到。若请求窗口足够、响应保持每拍一份，固定读取延迟可以被预取覆盖。

因此不能仅凭“G3排在第四”解释持续空转；要证明的是实际请求/返回或消费是否偏离该无气泡时间表。

## 5. 能静态算出的窗口条件，与不能擅自填的参数

GDG当前源码在读在途计数>=15时停止接收，额度在返回FIFO被AXI侧消费时才释放。这里L_token必须覆盖请求进入frame队列、MC/CDC和返回被消费的全过程，不只是DRAM物理读延迟；WL1标称32个请求事件不是这条链唯一窗口。

在一个独立、同钟、固定L_token的简化模型中，令请求在拍t被计数、对应返回在拍t+L_token消费。由于满15时halt不预先扣除同拍返回，第一次满窗后新请求最早在返回的下一拍恢复。其必要速率界为：

```text
request_rate <= min(1, 15 / (L_token+1))   [请求/AXI周期]
```

该式只针对上述固定延迟模型的15笔门控；真实多级队列、变延迟、共享请求和不同钟频要另行求解。它说明若窗口覆盖不了返回/消费延迟，就能仅由RTL和已知延迟推导周期性缺供，不需要wave；但当前未独立取得实际L_token，不能反过来用861拟合L_token再声称已经定位。

类似地，16路MC返回取最慢路、双Hub按序汇合、FIFO满、激活valid不足，都可写成明确递推条件。要得到唯一的完整周期，必须给这些接口的延迟/服务间隔及初始状态；shape和权重顺序只能确定请求序列，不能凭空确定这些输入。

当前本地MC wrapper引用的frame2array_aux、mc_frame2frame_aux、vmc_top_aux等完整模块定义未找到；tRC、splicing、刷新等还是可写配置，不能拿默认值替代当前VCS配置。这是静态模型尚未闭合的具体缺项，不是笼统地说“只有wave才能分析”。

## 6. 静态门控还能解释已知MTC相对差

对同一N512/k4，values总请求仍512次。每个内部C-minitile边界有1拍显式请求门控，最后一次结束不影响剩余values请求：

| MTC | C-minitile数 | 内部请求气泡数 | 理想values请求跨度 | 已有实测稳态，仅作对照 |
|---|---:|---:|---:|---:|
| 16 | 4 | 3 | 515 | 863 |
| 32 | 2 | 1 | 513 | 861 |
| 64 | 1 | 0 | 512 | 860 |

静态模型预测c16相对c32多2拍、c32相对c64多1拍，与已有差值一致。这能解释一项小的相对成本；不证明完整稳态等于请求跨度再加固定348，更不把这个差额命名为某模块等待。

## 7. 收敛结论

- 当前布局和固定顺序能静态确定：每轮四组、每组16 KiB、每组两拍双Hub传输；G3应在G0之后6拍进入同一理想流水。
- 请求路径没有要求等当前组MAC/OL1完成才请求下一组；因此“组3天然来不及”不是该分组必然造成的结果。
- 本地RTL显式循环门控仅解释上述少量minitile切换气泡，不能解释持续的大幅差距。
- 下一步静态求解应补MC服务/延迟、窗口释放和AL1/OL1切换条件；若这些参数齐全，完全可以不靠wave推导。当前不能在参数缺失时把无阻塞理想513拍升级为完整硬件必然耗时，也不能声称已静态推导出861。

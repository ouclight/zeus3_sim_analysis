# M1/k4：10拍MAC间隔的credit事件链

本轮在原单核8-group台架上增加只读C++事件采样，复用原Verilator RTL对象；不改生产RTL、不改MC/PHY参数、不强制ready、不改变credit深度。配置仍是M1/local/N512/w1/c32/k4，三块连续生产描述符，PE/MC半周期1250ps、部署PHY返回模型。

本轮重跑已完成：FP32输出1536项通过；256条lane事务守恒、64个PE检查通过。新增日志前后71469条原始事件记录完全相同；完成周期1161、2032、2903，稳态仍为871。全部三块96处10拍MAC间隔均通过“额度释放→恢复请求→9拍CAS间隔→10拍MAC间隔”关联断言。group0/group7采样的在途计数递推均通过。

lane0共1539笔（1536权重＋3索引）请求/释放配对：寿命22拍1356笔、35拍110笔、27拍48笔、28拍24笔、29拍1笔。采样的Hub0/lane0没有返回/消费反压。全256条lane中128条return_block/sink_block均0，另外128条均为3拍，不能宣称全核从无反压；本轮96处关联边界的归因以已逐拍核验的通路为准。

## 1. 采样范围和验证方法

新增group0与group7的Hub0/lane0状态：在途计数、halt、GDG请求FIFO、返回FIFO、MC状态、请求/接收/命令/返回/释放/消费事务计数。其余256-lane守恒、64-PE数值检查以及原有全部group MAC日志继续保留。

采样发生在核心上升沿之前，`cyc`与原SV日志一致。相邻样本中`accepted`或`released`增加，表示前一个样本所在周期发生请求或额度释放。Verilator优化后部分模块输入/输出端口副本不持续更新，不能用那些恒零副本判断握手。本轮采用实际SV事务计数差、有效内部状态和原MCSTEP/COMPUTE交叉验证，并断言：

```
outstanding = accepted - released
next_outstanding = outstanding + request_handshake - return_handshake
halt = outstanding >= 15
```

原始EV日志保留未作为证据使用的端口副本；分析脚本明确不以`req_axi2frame_rreq_send`等优化后的副本统计请求。

## 2. 原因：15笔在途窗口不能覆盖持续请求所需的返回往返

生产`gdg_flowctrl.v`在`rdata_outstanding>=15`时拉高halt；`gdg_axi2frame.v`将请求ready定义为`!frame_fifo_full && !flow_ctrl_halt`。额度不是在CAS发出时释放，也不是等OL1完成后释放，而是在`gdg_rdata_buffer.v`中的返回数据valid与ready同时成立时释放。

同一物理行内的普通请求，从GDG接收到释放额度实测22拍；释放当拍halt仍由旧计数15决定，下一拍才可重新接收。因此同一额度再次用于请求相隔23拍，形成典型“15拍有请求＋8拍无请求”的循环。这里22/23是新增事务序号配对得到的请求/额度时序，区别于此前恰好也为23拍的CAS→MAC传播差；二者不能混用。

首次开行及跨行请求另有更长寿命，不应把所有请求统一假设为22拍。完整统计见analysis.json。

## 3. 第一处10拍的逐拍证据

| 周期 | 实际事件 |
|---|---|
| 255–269 | 连续接收15笔本块权重请求，在途计数由0增至15 |
| 270开始 | outstanding=15，halt=1，不能再接收请求 |
| 285 | 请求FIFO已空；旧CAS流水仍在排出数据 |
| 286 | 发出col14的CAS |
| 287–294 | 没有CAS；MC ready保持1，体现缺请求而非该处MC换行等待 |
| 290 | 首笔权重在GDG返回缓冲被接收，释放额度 |
| 291 | outstanding=14，halt解除，接收下一笔请求 |
| 293 | 请求到达MC输入 |
| 295 | col15发CAS，距col14相隔9拍 |
| 308 | 上一次MAC有效（对应col13作为第二半） |
| 318 | 下一次MAC有效（对应col15作为第二半），间隔10拍 |

col14已经先到，但它只是下一次MAC操作数的一半；col15未齐备，不能发射。该边界在MAC窗口内最终暴露8拍增量。首次请求停发时间较长，其中一部分被启动流水掩盖，不能把所有halt拍数直接加到MAC窗口。

第二轮更直接显示持续周期：291–305接收15笔；306–313额度满；313释放下一轮首笔额度；314恢复接收。291→314=23拍，包含15拍请求和8拍停发。

## 4. 为什么每块32次

每条lane每块512笔权重，当前物理映射每行128笔，共4行。同一行内CAS空洞位于新列号15、30、45、60、75、90、105、120之前：每行8处，4行32处。每处CAS从本应相隔1拍变为9拍；两笔组成一次MAC发射，因此所在MAC间隔从2拍变为10拍。

15笔窗口是奇数，所以MAC边界编号呈7、15、22、30等交替，而不是每次固定隔8次MAC。不能据此把空洞解释为MTK四个逻辑输出组之间的切换。

## 5. 为什么缓存没遮住，以及Roofline的含义

本轮关联的Hub0/lane0返回数据按顺序被及时接收；其它部分lane有每轮合计3拍的接收阻塞，不能扩大为全核零反压。上一轮与本轮保留的lane统计可检查return_block、sink_block；当前M1没有用M4式权重复用降低新权重需求。暂停请求后，已有请求和数据流水逐步排空；返回数据不在手中时，增大一个闲置缓存并不能自动产生数据。要隐藏这类延迟，须有足够在途窗口与预取库存，且相应返回容量安全匹配，不能只取消halt。

算术/原始接口容量下界仍取`max(256,512)=512`，不能相加。实际模型还受到窗口持续吞吐限制：普通行内15笔/23拍，约为峰值的65.2%；这是该请求寿命及窗口配置下的局部持续速率，不是普适硬件峰值。有限物理行、开行和指令交接使整个块不能简单用512×23/15精确计算。

当前精确窗口账目：

```
MAC发射窗口 = 511 + 32×8 + (13+14+13) = 807
连续块稳态 = 807 + 64 = 871
```

511已经包含理想供数/计算重叠；256是窗口限制传到MAC后的增量；40是三处跨行增量。块间64仍需单独分解。

只改编译器/kernel时，MTK交错减少OL1反馈依赖，但不会扩大这个硬件在途窗口，也不会让M1获得M4的权重复用。减少实际权重流量、增加真实输入行复用、或者改变合法执行路径才可能从软件侧改变这项约束；仅改变等流量布局，不保证消除该限制。本轮没有验证新的优化配置。

# PEC/L2保持不变，接入真实权重返回链：本地逐周期结果

2026-10-29。不修改设计RTL，不使用wave，不提交远端任务。承接[PEC＋L2理想权重基线](PE_PEC_L2_RTL_RESULTS_20261029.md)。

## 1. 结论和完成情况

已将理想权重源替换为 **真实GDG额度控制/返回FIFO → Hub请求和响应汇合 → WL1读取控制/数据整理 → PE**。保留前轮PEC、L2、AL1/MAC/OL1、group输出FIFO/credit以及1536个FP32的L2回读验证。

三组均通过全部数值和计数门控：

|配置|MC服务模型|第二/第三条MAC窗口（含首尾）|相邻PEC完成间隔|
|---|---|---:|---:|
|前轮理想源|直接每2拍向PE供一批|511 / 511|515 / 515|
|本轮低延迟|LAT=4，II=1|512 / 512|**529 / 529**|
|延迟对照1|LAT=14，II=1|613 / 613|**640 / 640**|
|延迟对照2|LAT=23，II=1|919 / 919|**955 / 955**|

LAT是人为设置的MC请求到可返回数据的模型参数，II=1表示最多每拍返回一次。它们不是远端测得的延迟，也不是从861倒推后填入的硬件参数。

**接入该真实返回链后，低延迟、无其他客户竞争时，仍未产生接近861的块内持续限制。** 延迟对照则实际产生了可追踪的“返回空洞 → MAC空洞”，不再只是根据总耗时猜测供数问题。但本轮仍未复现远端861的实际根因，未接真实MC物理服务及完整系统争用。

## 2. 确切模型边界

生产RTL模块：
- gdg_flowctrl：真实未完成请求额度门控。
- gdg_rdata_buffer：真实返回FIFO及额度释放。
- wl1_518_hub_mc_req_ctrl：MC请求/响应控制。
- wl1_518_hub_weight_req_distribute：16路请求分发/响应汇合。
- Hub返回link_pipe，按此前Hub配置的一层返回流水。
- wl1_518_weight_rd_ctrl、wl1_518_weight_data_format：双Hub响应接收、数据整理、输出FIFO及PE反压。
- 前轮已接入的PEC、L2、group入口CDC、真实AL1/MAC/OL1、group sum/DT、输出FIFO/额度控制保持不变。

仍是测试驱动的部分：
1. **MC服务**：每个通路独立按请求排队，LAT拍后可返回，受II限制，返回全1 BF16数据。没有实际MC物理阵列、地址相关服务时间或其他MC客户。
2. **WL1地址生成**：每条512笔顺序请求；第256笔处保留前轮地址请求模型的一拍间隔。未接生产WL1索引发生器，因此这拍不能称为已验证的生产开销。
3. **跨指令权重调度**：从PEC命令识别三条execute，等待真实formatter的inst_done后，经过测试调度器启动下一条。未接完整生产WL1指令调度器。
4. **全核简化**：保留前轮两类代表group（每类实例8个真实PE），按PEC的5级/2级路径映射到8group接口，各代表拥有独立返回链。每条返回链为双Hub、每Hub16个MC通路。没有模拟8group共享物理MC或两核竞争。
5. 同频同相时钟、ECC关闭、没有其他L2客户；仍为三条M1/N512/K4096、w1/c32/k4合成指令。

权重现在确实经过返回链和formatter进入MAC，没有从旁路提供常量权重。常量位于MC服务模型的数据返回端。全1数据沿用前轮，能检查计算结果、丢失/重复数量及回写，但不能独立验证任意权重索引排列的正确性。

## 4. 低延迟组为什么是529，而不是515

以第二条命令为例，真实握手日志为：

|事件|首拍|末拍|数量|
|---|---:|---:|---:|
|测试调度器启用本条返回链|779|—|—|
|WL1地址请求接受|780|1292|512笔|
|WL1接收双Hub整理前返回|792|1304|512笔|
|PE/MAC接收权重|795|1306|256批|
|formatter指令完成|1307|—|1|
|PEC完成通知|1365|—|1|

请求间隔：510次1拍、1次2拍；返回间隔完全相同。唯一一拍额外空洞来自保留的测试请求源间隔。经过两拍数据组装后，MAC间隔为254次2拍、1次3拍。

下一条首MAC在1324拍：
```text
1306  本条最后MAC
1307  formatter确认完成
1308  测试调度器启动下一条
1309  下一条首请求被接受
1321  下一条首返回被WL1接收
1324  下一条首MAC
```

因此稳态首MAC间隔为：
```text
本条首MAC→末MAC：511拍
本条末MAC→下条首MAC：18拍
合计：529拍
```

相对前轮515，多出的14拍不能直接叫“真实WL1固定开销”：请求源本身多1拍间隔，且跨指令调度/重新填充的边界与直接权重源不同。这里的529是当前隔离模型实测，不是生产RTL的不可突破下界。

## 5. 延迟对照：空洞从哪里传到MAC

观察第二条命令，第三条相同：

|统计|LAT4|LAT14|LAT23|
|---|---:|---:|---:|
|WL1返回相邻间隔|510×1拍 + 1×2拍|477×1拍 + 34×4拍|477×1拍 + 34×13拍|
|MAC相邻间隔|254×2拍 + 1×3拍|221×2拍 + 34×5拍|221×2拍 + 34×14拍|
|MAC窗口内权重valid为0|256|357|663|
|权重valid而PE不ready|0|0|0|
|激活valid为0|0|0|0|
|ALU命令不ready|0|0|0|
|监测ALU流水不ready|0|0|0|
|请求valid而请求端不ready|0|95|383|
|WL1返回valid而formatter不ready|0|0|0|

这些计算侧统计取代表group0的PE0，pipe_ready取ALU控制第0路；所有PE之间的ready对称断言也通过。

**权重valid为0不能全部当作异常stall。** BF16需要两拍返回才能组成一批MAC权重，正常工作本来就有交替的无新权重拍。延迟对照的证据是超过正常两拍的接收间隔增加，并且同样的间隔先出现在WL1返回数据上。

在这两个受控延迟场景下，数据未能持续到达；数据一旦到达，PE能接收。没有观察到计算窗口内formatter接收端反压，更没有观察到AL1或OL1/ALU ready导致这些间隔。

## 6. GDG额度统计怎么理解

以下为代表group0、Hub0/MC0，三条命令全程统计；完整64个实例通路的结果见JSON：

|统计|LAT4|LAT14|LAT23|
|---|---:|---:|---:|
|接受请求/返回/释放额度|1536/1536/1536|1536/1536/1536|1536/1536/1536|
|观察到的最大未完成请求数|15|15|15|
|flow_ctrl_halt拍数|33|333|1233|
|GDG返回valid但下游不ready拍数|40|27|9|
|请求接受到释放额度的最短间隔|7|17|26|
|对应最长间隔|47|44|35|

LAT4也能在启动期达到15笔、产生halt和返回反压，因此**“达到15”或“出现halt”本身不能证明稳态受限**。该组后两条MAC窗口的请求端/返回端反压均为0。

LAT14/23中，最短额度驻留时间已经超过15拍窗口的理想一拍一笔维持条件，且真实请求门控及返回空洞增多。该结果支持“有限额度窗口与服务/回收延迟共同限制持续供数”的机制，适用于本轮设定的服务模型。这里观测的7/17/26是当前仿真请求接受到额度释放的计数，和输入参数LAT不同。

最长驻留时间包含启动期消费者未准备好导致的等待；不能拿全程最大值去预测稳态带宽。表中各类等待也不能直接相加，存在重叠。

## 8. 对后续根因定位的约束

本轮已经确认：这组真实返回/计算模块在低延迟、无竞争条件下，能够以约512拍完成块内供数和MAC接收。继续仅改变合成矩阵shape或重复扫描人为LAT，不能证实远端861原因。

要进一步接近生产，需要优先消除尚未匹配的边界：
1. 用生产WL1指令控制及索引发生器替代当前线性请求/跨指令调度器，检查是否自然出现额外请求空洞。
2. 核对生产MC服务、共享仲裁和时钟配置；若本地缺少对应实现，明确停在该边界，不能靠调LAT到相似cycles来宣称复现。
3. 若能接入实际共享MC服务，将同样的请求/返回/释放及MAC间隔统计保留，比较新增空洞首次出现的位置。

远端861−本轮529的332拍仍然不是某个模块已测得的等待时间。本轮收获是可运行、可数值验证、能追踪供数空洞传播的模型，以及被明确缩小的未匹配范围。

# 真实Hub共享仲裁：固定MC服务的受控对照

2026-10-29。接入完整生产wl1_518_hub，保持MC模型LAT=4、II=1、生产WL1指令/地址控制、PEC/L2、计算和数值回读门控不变。生产RTL未修改。

## 1. 核心结果

**真实共享仲裁中的DIN竞争，可以在MC服务参数不变时显著降低权重持续吞吐。**

|同一可执行模型的运行配置|第二/第三条MAC窗口（含首尾）|PEC完成间隔|
|---|---:|---:|
|无DIN，无uscale|511 / 511|**521 / 521**|
|DIN读：接受一笔后至少间隔4拍再发下一笔|676 / 676|**686 / 686**|
|DIN读：每拍尝试，遇反压保持请求|848 / 847|**858 / 857**|

三组全部通过1536个FP32的真实L2回读、实际权重地址序列和请求/返回/额度计数校验。

本轮有两项不同结论：
- 已证明：在实际Hub仲裁RTL中，加入DIN读流量会导致权重请求失去服务、出现MAC供数空洞，完成间隔增大。
- 尚未证明：原生产861拍任务计算期间存在本轮这样的DIN流量。**858与861接近，不代表已复现生产根因；不得据此倒推真实DIN请求速率。**

DIN负载是显式构造的诊断源，没有从生产trace提取。没有调整MC延迟去拟合861。

## 2. 先纠正共享拓扑的假设

此前讨论中“把8个group接到同一MC仲裁器”的示意不符合本地所核RTL连接。

当前可见连接：
- pegroup518_x8_top分别实例化8个group，各自映射到o_pegN_wl12dram_*等存储接口；
- 每个pegroup518_top内部实例化自己的wl1_518_top；
- WL1内部有双Hub；
- **每个Hub的16个MC通路，各有DIN/RMW、weight、uscale三类请求共享的仲裁器**。

证据：
- pegroup518_x8_top.v:1086及1277等位置，group0/group1同名局部存储输出连接到不同顶层信号；
- pegroup518_top.v:528实例化本group的WL1；
- wl1_518_hub.v:543开始，16个wl1_518_hub_mc_req_ctrl；
- wl1_518_hub_mc_req_ctrl.v:262：
  ```verilog
  w_rr_request = {i_in_rd_2_vld, i_in_rd_1_vld, w_rmw_rd_0_vld};
  ```
  三个槽分别为uscale、weight、DIN/RMW。

因此本轮没有人为添加8group公共MC仲裁器，也不能因存在共享仲裁就把全核条件带宽除以8。拓扑审计保存在topology_audit.json。

这不等于已经核验所有跨核物理资源及远端版本；结论限定当前本地RTL可见的连接层级。

## 3. 本轮实际连接

```text
真实WL1 weight_ctrl ──权重广播请求──┐
                                 │
诊断DIN读源 ──真实DIN分发器────────┼→ 完整生产Hub
                                 │    每MC真实轮询仲裁
uscale关闭───────────────────────┘          ↓
                                      GDG额度/返回FIFO
                                           ↓
                                  同一个LAT4/II1 MC模型
                                           ↓
                                  按真实请求次序返回
                                           ↓
                       权重汇合 → formatter → MAC/OL1
                       DIN汇合  → 诊断数据校验
```

相较前轮手工拼装collector和MC请求控制，本轮使用完整wl1_518_hub，包含实际入口流水、DIN分发、权重分发、三类请求仲裁及返回排序。

原有两类计算group代表仍保留，每个实例含8个真实PE；没有扩展成64个彼此独立的PE。由于所核拓扑没有8group公共读仲裁器，不需要为这个Hub内共享点人为合并各组权重接口。

## 4. DIN负载具体是什么

- 每Hub从约200拍开始发DIN读，直到其计算group消费完原有768批权重。
- 每笔DIN为128B，经真实DIN分发器访问4个MC。
- 地址依次递增，使请求轮流访问MC0～3、4～7、8～11、12～15。
- 权重请求仍使用同一Hub的16个MC，每通路各1536笔，权重工作量不变。
- DIN地址在独立区域；MC返回全1 BF16，DIN返回数据也逐笔校验。
- DIN4在一笔被接受后，至少4拍再发下一笔；若ready为0则保持valid和地址，所以这不是保证每4拍必定接受一笔。
- DIN1每拍尝试，同样遵守反压。
- 结束必须等待全部DIN返回；不会在PE结果出来后直接丢弃尚未完成的诊断请求。

没有DIN写、部分写/RMW或uscale流量。本轮只覆盖DIN读与权重读的竞争。

## 5. 直接观察到的仲裁证据

以下为代表group0、Hub0、MC0，统计覆盖三条命令全程：

|统计|无DIN|DIN4|DIN1|
|---|---:|---:|---:|
|weight获得服务次数|1536|1536|1536|
|DIN获得服务次数|0|133|653|
|总请求/返回/释放额度|1536/1536/1536|1669/1669/1669|2189/2189/2189|
|权重待处理、DIN获grant并被MC接受|**0**|**127**|**343**|
|GDG返回valid但下游不ready拍数|52|416|428|
|flow_ctrl_halt拍数|31|22|17|

“权重待处理、DIN获服务”使用实际RTL信号计数：
```text
w_rr_request[1] = 1
w_rr_granted[0] = 1
实际MC请求 valid && ready
```

它表示该拍真实服务了DIN而权重请求仍待处理，不是从总耗时估计的“可能仲裁等待”。

halt反而下降，而耗时上升，说明不能只凭GDG是否达到15笔或halt总数来判定瓶颈。加入DIN后，实际仲裁、返回排序及汇合的时序共同变化。

上表是一个MC通路的计数。跨64个仿真实例求和的仲裁冲突为0/8208/21936，单位是“通路×拍”，不能把它直接当作全核额外周期或与完成时间相加。

|请求valid但ready低（窗口内）|1|165|333|

|权重valid但PE不ready|0|0|0|
|激活无效|0|0|0|
|ALU命令不ready|0|0|0|
|监测的第0路ALU流水不ready|0|0|0|

计算端统计限定代表group0的PE0；其他PE的ready对称检查保留。两类group之间由于DIN竞争相位不同，MAC事件偏移不再始终固定3拍，完整事件见JSON。

本轮因果对照是：
```text
只加入DIN读请求
   → 真实仲裁器服务DIN，部分待处理权重未获服务
   → 权重请求端反压增加，返回节奏产生间隔
   → MAC接收从每2拍一次变为2/3/4/5拍混合
   → 完成间隔增加
```

这组测试能把减速归于加入共享DIN负载所引起的链路行为。不能进一步将每个新增周期唯一分配给仲裁、GDG FIFO或Hub汇合，因为它们重叠并相互反压。

DIN4的MC0额外请求约为权重请求的8.7%，但连续完成时间增加约31.7%。因此按新增字节比例估计代价并不充分；还包含16路权重广播/汇合、请求相位、排序与缓冲的时序影响。本轮未把这些影响逐项拆成互斥周期。

## 8. 数值、地址和计数门控

三组均通过：
- 1536个FP32从真实L2回读，全部等于4096；
- 真实解码字段保持TC4095、TK511、WC511、WSTMOD1、WIDXEN0；
- 三条各256次MAC接收，每个代表group共768次；
- 每条512笔实际权重地址与前轮逐笔一致；
- 每MC通路1536个weight grant及其MC地址序列核验；
- 总MC请求数=返回数=额度释放数=weight grant+DIN grant；
- 每Hub所有DIN请求全部返回且数值正确；
- 每笔DIN对应4次MC服务，Hub内DIN grant总数=4×DIN接受笔数；
- 无PEC错误、Hub/formatter/GDG FIFO溢出或额度错误。

每个Hub接受并返回的DIN笔数：

|无DIN|0 / 0|0 / 0|

各group停止DIN的周期按自身完成决定，存在少量笔数差异；它们不是生产任务实际DIN读取量。

## 9. 对861根因的实际含义

现在可以确定：
1. 在本地所核拓扑中，不能继续用“8group共同争用一个MC读仲裁器”解释低吞吐。
2. 真实Hub内DIN/weight共享竞争确实能把当前计算拖到约858拍；MC的LAT/II完全没变，计算量和权重工作量也没变。
3. 无DIN、UEN=0时，完整Hub仍为521拍，所以“有仲裁模块就必然降到861”不成立。

下一项证据应当是**生产861任务在PE计算窗口内，DIN/weight/uscale三类输入的实际请求及grant数量**。如果生产窗口DIN和uscale均无请求，本轮测到的竞争机制就不能解释那个任务；应继续检查实际MC服务、时钟及版本等差异。不能用“858接近861”取代这一步。

# 生产WL1指令与地址控制接入：本地逐周期仿真结果

2026-10-29。保持MC模型LAT=4、II=1，PEC/L2、输入/权重数值和1536个FP32回读校验不变。仅修改本地仿真连接和测试驱动，未修改生产RTL。

## 1. 核心结果

**三条连续指令全部通过，两个PEC完成间隔均为521 cycles。** 前轮人工请求/调度模型为529拍；本轮由生产WL1控制自然产生的间隔减少8拍，未出现接近861拍的持续阻塞。

|模型|后两条MAC窗口（含首尾）|PEC连续完成间隔|
|---|---:|---:|
|理想权重直接送PE|511 / 511|515 / 515|
|真实返回链＋人工地址/调度|512 / 512|529 / 529|
|真实返回链＋生产WL1指令/地址控制|**511 / 511**|**521 / 521**|

三者保留各自模型边界，不能将521视为远端系统的必然时间或把861−521直接归因于某模块。

## 2. 具体替换内容

新增实例化生产模块：
- wl1_518_inst_ctrl及内部指令FIFO、解码、输出控制；
- wl1_518_weight_ctrl，包含实际地址计数/状态机、读取控制、指令参数流水FIFO和formatter。

连接改为：
```text
PEC的WL1命令
   → 真实inst_ctrl
       → 解码字段 → 真实weight_ctrl → 原Hub/GDG/MC模型
       → 输出命令 → group sum/DT指令控制
       ← group完成、weight_ctrl完成
   → 真实指令额度返回PEC
```

移除了人工active/issued/sent/bubble_done调度、线性地址生成和“消费完再启动下一条”的逻辑。以前由测试代码强行指定的外层计数，也改由weight_ctrl依据解码字段计算。

保留前轮两类group代表、真实计算及L2链路。inst_ctrl接在同钟CDC后接口；没有实例化整个WL1 top的无关APB、DMA和uscale通路，UEN=0。MC物理服务仍是模型，未加入共享MC/多核争用。

## 3. 指令字段及地址审计

由于前轮直接驱动formatter，不需要实际解码权重配置；本轮补入：
- WC=511：local V-cache下的物理输出宽度减1；
- WSTMOD=1、WIDXEN=0：V-cache、非索引表模式；
- WSADDR=0x100000：由生产控制剥离group位后，实际请求基址为0x20000；
- TC=4095、TK=511，保留w1/c32/k4。

源码转换为：
```verilog
INST_WSADDR = {i_wl1_inst_wsaddr[33:14],
               i_wl1_inst_wsaddr[10:0]};
```
见 wl1_518_weight_ctrl.v:1252。不是普通的“所有地址统一右移3位”；它保留低11位、去掉中间3个group位。本用例基址对齐，转换结果等价于缩小8倍。

最终每条实际接受的权重请求均为：
```text
0x20000, 0x20400, 0x20800, ... 共512笔，每笔递增1024
```
三条的序列都与前轮一致。64个MC实例通路各自的实际地址序列也逐笔验证为128～639，重复三次。不是仅凭全1输出正确来判断地址正确。

首次编码曾把0x20000直接作为WSADDR，实际基址变成0x4000；该次记录保留为unmatched_base.log，不作为最终地址匹配对照。修正后周期结果不变，符合当前MC服务不依赖地址的模型设定。

合成指令多一个权重基址配置字，首条启动周期与前轮不完全相同；本结论比较连续完成间隔。

## 4. 周期结果

代表group0（PEC 5级路径）：

|命令|首MAC|末MAC|PEC完成|
|---|---:|---:|---:|
|0|270|778|837|
|1|789|1299|1358|
|2|1310|1820|1879|

另一类group（2级路径）的MAC事件均提前3拍。

后两条各256次MAC接收，相邻255个间隔全部为2拍：
- 首末MAC相差510拍，含首尾窗口511拍；
- 本条末MAC至下一条首MAC相差11拍；
- 连续间隔为510+11=521拍。

这里511与按256批×2拍计的512拍是端点口径差异。首条509拍含预取形成的两次1拍间隔，不是持续带宽超过条件容量。

末MAC至PEC完成均59拍，与下一条计算重叠，不另行串加进稳态时间。

## 5. 真实地址控制有没有空拍

**有，但只有局部空拍，没有造成块内MAC空洞。**

|命令|首请求接受|末请求接受|请求数|地址控制主动暂停周期|
|---|---:|---:|---:|---:|
|0|213|755|512|499|
|1|763|1276|512|1020|
|2|1284|1797|512|1541|

上述主动暂停周期均观察到：
```text
指令有效=1，准备完成=1
TC切换flag=1，TK切换flag=0
ADDR_CNT_DELAY_FLAG=1
请求valid=0，下游ready=1
```
这次暂停来自真实weight_ctrl，不是测试驱动插入。源码请求条件位于wl1_518_weight_ctrl.v:1363附近。

第二条请求接受间隔为509次1拍、2次2拍：
- 一次是1020拍的TC地址切换暂停；
- 另一次在788拍，请求valid=1但ready=0，属于请求接收反压，不是地址发生器主动停止。它发生在第二条首MAC789拍之前。
第三条具有相同的间隔分布。

这些请求间隔被返回链/FIFO预取覆盖，第二、三条的MAC仍严格每两拍接收一次。不能将“请求有空拍”直接等同于“计算损失同样拍数”。

## 6. 为什么比人工模型快8拍

真实指令控制允许请求与上一条剩余计算重叠：
- 第二条首请求763拍发出，第一条末MAC778拍才发生，提前15拍；
- 第三条首请求1284拍发出，第二条末MAC1299拍才发生，同样提前15拍。

这是生产weight_ctrl将请求完成与数据消费完成分离的实际效果。其o_weight_cmd_done由请求结束及指令流水FIFO空间控制，不要求整个PE计算完成。

人工模型中，后两条MAC窗口为512拍、末MAC到下条首MAC间隔18拍；本轮为511拍和11拍。因此连续间隔从529降到521：
```text
旧模型：511（首末差）+18（边界间隔）=529
新模型：510（首末差）+11（边界间隔）=521
```
这只是模型连接改正后的差异，不是修改生产RTL获得的8拍优化。真实TC切换暂停仍存在，只是没有在MAC窗口中留下额外间隔。

## 7. 数值和等待门控

全部通过：
- 真实解码字段核验：TC4095、TK511、WC511、WSTMOD1、WIDXEN0；
- 三条各256次MAC；每个代表group共768次；
- 64个MC通路各1536次请求/返回/额度释放，数量一致；
- 请求端和MC端地址序列逐笔一致性检查；
- 192笔L2激活读取，48笔结果写入；
- 1536个FP32经真实L2回读全部为4096；
- 未触发WL1 FIFO溢出、地址溢出、GDG额度错误或PEC错误。

第二、三条MAC窗口内，代表group0的PE0：
- 激活无效、ALU命令不ready、所监测第0路ALU流水不ready均为0；
- 权重valid但PE不ready为0；
- 请求valid但ready为0、返回valid但formatter不ready均为0。

全程L2读端握手等待696拍、写端等待0拍；读端等待与计算重叠，不能直接加到521上。初始预取阶段存在返回和请求反压，因此以上“0”等待结论限定后两条MAC窗口。

审计说明：第一次运行因测试断言把o_intr_inst_fifo_empty当成错误而停止。该信号实际是FIFO为空的状态，复位时正常为1；已修正观测判断，未关闭溢出和数值检查。无效日志保留为rejected_empty_status.log。

## 8. 可得结论和下一边界

在本轮LAT4/II1、无其他客户竞争、同钟的条件下：
1. 生产WL1地址控制确实有TC切换空拍，但没有形成持续的额外MAC间隔。
2. 真实指令调度允许提前发下一条请求，人工调度器此前偏保守。
3. 接入生产控制后仍为521拍，不能用这部分逻辑解释远端861的数百拍差距。

剩余主要未匹配边界是实际MC服务、共享仲裁/多核竞争、时钟及远端实现版本、完整生产程序的运行环境。当前两类代表group各有独立返回链，并非8group共同争用实际存储系统。继续核查这些边界，比再次凭形状猜测WL1固定停顿更有针对性。

本轮全1数据不能证明任意数值和任意布局都正确；地址序列审计补足了当前用例的地址检查，但没有替代生产张量回放。
